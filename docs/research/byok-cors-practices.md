# BYOK CORS Practices — Research for arxa studio (hosted web)

Date checked: 2026-08-04. Question: for a hosted web app where users supply their own LLM API key, should we call providers directly from the browser (CORS) or relay through a same-origin server proxy?

Net read: Anthropic is the only provider in this set with a documented, supported, opt-in CORS mechanism intended for direct browser use. Everyone else either actively blocks it, discourages it in official docs despite technical reachability (Gemini), or is simply undocumented (DeepSeek, Moonshot, Z.ai) — and undocumented CORS behavior is not something to build a production feature on, since providers can add `Access-Control-Allow-Origin` restrictions at any time without notice.

## 2. BYOK product precedent

| Product | Key storage | Direct vs. proxy | User warning / notes |
|---|---|---|---|
| OpenRouter (BYOK) | Provider keys stored **server-side**, encrypted, associated with the user's OpenRouter account — not held in the browser at all | Proxy (OpenRouter is itself the relay; it calls providers server-side and adds provider-key-priority/fallback logic) | Docs emphasize key rotation and scoping (per-key filters, member filters) rather than any client-storage warning, because the key never touches the browser | [OpenRouter BYOK docs](https://openrouter.ai/docs/guides/overview/auth/byok) |
| TypingMind | Browser **localStorage**, AES-encrypted at rest in the browser | Direct-from-browser to provider (client app, no TypingMind-operated backend in the request path) | Marketed as "your key never leaves your browser except to the AI provider" | [awesome-byok-apps list](https://github.com/yatsyk/awesome-byok-apps) |
| Chatbox | Browser/local app storage | Direct-from-browser or local desktop client | Cross-platform desktop/mobile client, BYOK by design | [awesome-byok-apps list](https://github.com/yatsyk/awesome-byok-apps) |
| big-AGI | Browser storage | Direct-from-browser | Multi-model workspace, BYOK | [awesome-byok-apps list](https://github.com/yatsyk/awesome-byok-apps) |
| LibreChat | Server-side (self-hosted backend) | Proxy (keys pass through the user's own self-hosted server, not the public browser) | Self-hosting shifts trust boundary to "you trust your own server," a materially different model than a third-party-hosted BYOK relay | [OpenSourceDiscovery #97: LibreChat](https://opensourcedisc.substack.com/p/opensourcediscovery-97-librechat) |
| Google AI Studio (exported Cloud Run apps) | Server-side env var (`GEMINI_API_KEY`), never sent to the browser | Same-origin transparent proxy — a service worker intercepts calls the frontend code makes to `generativelanguage.googleapis.com` and redirects them to the local Node backend, which injects the key | Explicit rationale: avoids "leaking the key to the browser" while keeping frontend code that looks like it's calling Google directly | [Google AI Studio proxy writeup](https://glaforge.dev/posts/2026/02/09/decoded-how-google-ai-studio-securely-proxies-gemini-api-requests/) |
| Cloudflare AI Gateway (BYOK feature) | Provider keys stored server-side in Cloudflare's Secrets Store | Proxy (gateway holds the key, client references it by config, never sees it) | Positioned as a managed alternative to rolling your own proxy | [Cloudflare AI Gateway BYOK docs](https://developers.cloudflare.com/ai-gateway/configuration/bring-your-own-keys/) |
| `byok-patterns` reference repo | Demonstrates all three: browser-only (localStorage), WordPress plugin (encrypted storage), Node proxy (zero deps) | Explicitly frames as a threat-model tradeoff, not "one correct answer" | Key framing: "browser-only = XSS in your code is key theft, zero infra. Proxy = server compromise is the risk, but logs must redact." Flags common mistakes: logging the key, putting it in a URL (leaks via browser history/referrer/analytics). | [0xelitesystem/byok-patterns](https://github.com/0xelitesystem/byok-patterns) |

Pattern: providers/products that already have a trusted server in the loop (OpenRouter, LibreChat, Google AI Studio exports, Cloudflare AI Gateway) proxy. Pure client-only tools with no backend at all (TypingMind, Chatbox, big-AGI) hold the key in browser storage because there is no server to hold it instead — that's a constraint of their architecture, not evidence it's the safer choice when a backend already exists.

## 3. Security guidance on browser key storage

- **OWASP** (HTML5 Security Cheat Sheet, Web Security Testing Guide): a single XSS can read and exfiltrate everything in `localStorage`/`sessionStorage`; don't store sensitive data there; prefer `sessionStorage` over `localStorage` when persistence isn't required. [OWASP HTML5 Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html); [OWASP WSTG client-side storage testing](https://owasp.org/www-project-web-security-testing-guide/v41/4-Web_Application_Security_Testing/11-Client_Side_Testing/12-Testing_Browser_Storage)
- **NIST 800-63B §7.1**: session-binding secrets SHOULD NOT be placed in insecure locations such as HTML5 Local Storage, due to XSS exposure (cited via multiple secondary sources reviewed above).
- **Cookies vs. localStorage**: `HttpOnly` + `Secure` + `SameSite` cookies are not readable by JavaScript, so XSS alone can't exfiltrate them (though they remain vulnerable to CSRF, mitigated by `SameSite`). `localStorage` has no equivalent protection — any injected script can read it outright. A "hybrid" pattern for high-sensitivity apps: `HttpOnly` cookie for a refresh token + in-memory-only storage for the short-lived access token, never persisted. [Session Token Security: Local Storage vs. Cookies](https://medium.com/@dub-flow/session-token-security-local-storage-vs-cookies-29a8c1c8aaa1)
- **Same-origin thin passthrough proxy, no persistence**: this is exactly the pattern Google AI Studio ships for Gemini exports (service-worker intercept → same-origin Node backend → inject key → stream response back), and is one of the three reference patterns in the `byok-patterns` repo. It is treated as acceptable/standard practice specifically *because* it removes the key from client-readable storage entirely — the key exists only in server memory/env for the duration of the relayed request. This is a materially different risk profile than either "key in localStorage" or "key in a third party's database" (as with OpenRouter/Cloudflare BYOK, where the *provider's own platform*, not the end user's device, holds custody).
- **Key-scoping / spend-limit features per provider**, relevant as a compensating control regardless of storage choice:
  - **Anthropic**: Workspaces let you set monthly spend limits and rate limits (RPM/TPM) per workspace/key, configured in the Console UI (no public API for this outside Enterprise). [Claude Platform Docs — Workspaces](https://platform.claude.com/docs/en/manage-claude/workspaces)
  - **OpenAI**: Project-scoped keys (`sk-proj-...`) isolate usage tracking, rate limits, and member access per project; project Owners can set hard spend limits that stop traffic once reached. [OpenAI — Managing projects](https://help.openai.com/en/articles/9186755-managing-your-work-in-the-api-platform-with-projects)
  - **Gemini**: Keys can be restricted by HTTP referrer / IP / app identity (application restrictions) plus API restrictions (which APIs the key may call) — but referrer-restricted keys will reject server-side calls, so this only helps for the direct-from-browser case, not a proxy. Google is also sunsetting unrestricted "Standard" keys in September 2026 in favor of service-account-bound auth keys. [Using Gemini API keys](https://ai.google.dev/gemini-api/docs/api-key)

## 4. The hybrid pattern: direct-where-CORS-works, proxy-where-not

Real-product precedent for exactly this split:

- **Anthropic direct + everyone-else-proxied** is architecturally the same shape Simon Willison used before Anthropic shipped CORS support: he ran his own Vercel-hosted CORS proxy in front of `api.anthropic.com` for his client-side Haiku app, then removed the proxy the moment Anthropic's native CORS opt-in shipped — i.e., the proxy was a stopgap specifically for the no-CORS case, dropped once direct access became available for that one provider. [Simon Willison — Claude's API now supports CORS](https://simonwillison.net/2024/Aug/23/anthropic-dangerous-direct-browser-access/)
- **Google AI Studio's exported apps**: same-origin service-worker + Node proxy specifically for Gemini, because Gemini has no equivalent browser-safe opt-in — this is a live, first-party (Google-authored) example of the "proxy where CORS/official support is absent" half of the hybrid. [Google AI Studio proxy writeup](https://glaforge.dev/posts/2026/02/09/decoded-how-google-ai-studio-securely-proxies-gemini-api-requests/)
- **Cloudflare AI Gateway / OpenRouter** generalize this to "proxy everything, regardless of per-provider CORS status," trading a small latency/infra cost for one uniform trust boundary instead of a per-provider special case.

No single product was found that documents *exactly* "direct-call Anthropic, proxy the rest" as a named pattern, but it falls out directly from combining (a) Anthropic's unique documented CORS opt-in with (b) the universal proxy-everything-else practice used by Google AI Studio, Cloudflare, and OpenRouter for providers lacking that opt-in.

## Recommended architecture (synthesis, ≤200 words)

Use a hybrid: call Anthropic directly from the browser with `anthropic-dangerous-direct-browser-access: true`, since it's the only provider with a documented, supported browser-CORS opt-in built for exactly this BYOK use case. For every other provider in scope (OpenAI, Gemini, DeepSeek, Moonshot/Kimi, Z.ai), route through a same-origin, non-persistent streaming passthrough proxy — a thin server endpoint that accepts the user's key + request per-call, forwards it, streams the response back, and never writes the key to disk, logs, or a database. This mirrors Google AI Studio's own exported-app architecture for Gemini and is one of the three sanctioned patterns in community BYOK reference implementations.

For key storage on the client: hold the key in memory for the session (a JS variable/store, not `localStorage`) where feasible; if persistence across reloads is wanted, `sessionStorage` is the least-bad browser-storage option per OWASP guidance, with `localStorage` avoided given XSS-exfiltration risk. Because arxa is hosted (not user-self-hosted like LibreChat), a compromised proxy is a shared-infrastructure risk — keep the proxy stateless and redact keys from all logging/error-reporting paths, and surface each provider's own scoping controls (Anthropic workspace spend caps, OpenAI project spend limits, Gemini key restrictions) to users as an additional compensating control.

| Provider | Endpoint | Status | CORS response |
|---|---|---|---|
| DeepSeek | api.deepseek.com/chat/completions | 200 | origin reflected, allow-credentials true, POST + authorization,content-type allowed (server: elb) |
| Moonshot/Kimi | api.moonshot.ai/v1/chat/completions | 204 | origin reflected, allow-credentials true, POST + authorization,content-type allowed (server: cloudflare) |
| Z.ai GLM | api.z.ai/api/paas/v4/chat/completions | 200 | origin reflected, allow-credentials true, max-age 3600 (server: TencentEdgeOne) |
| Z.ai GLM | open.bigmodel.cn/api/paas/v4/chat/completions | 200 | same as api.z.ai |

**Conclusion:** all three open-weight providers currently permit browser-direct calls via reflected-origin CORS. None document or commit to this behavior (contrast: Anthropic's documented opt-in header). Reflected-origin permissiveness can be withdrawn silently; treat as working-today, not contractual.
