# Safely Rendering & Streaming Model-Generated Interactive UI in a Chat Thread

Research date: 2026-08-21/22. All sources fetched and dated below; anything not independently verified is flagged **[unverified]**.

---

## 1. Isolation options and their trade-offs

### `<iframe sandbox="...">`
The `sandbox` attribute forces the framed document into a "different origin" state by default — no scripts, no forms, no popups, no top-navigation, treated as opaque-origin — and you re-enable only the flags you need (`allow-scripts`, `allow-forms`, `allow-popups`, `allow-downloads`, `allow-modals`, etc.). [MDN — `<iframe>`](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe), [MDN — CSP `sandbox` directive](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/sandbox).

**The classic footgun:** `allow-scripts` + `allow-same-origin` together, when the framed document is served from the *same origin* as the parent, let the framed document call `document.querySelector('iframe').removeAttribute('sandbox')` — i.e. it can strip its own sandbox and become fully privileged, same-origin script access to the parent DOM included. MDN states this "make[s it] no more secure than not using the `sandbox` attribute at all." [MDN iframe](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe). Shipping the two flags together is safe **only** if the framed content is served from a genuinely different origin — same recommendation from web.dev: "you need to be very careful when dealing with framed content that comes from the same origin as the parent" and should serve sandboxed content from a separate origin to limit damage. [web.dev — Play safely in sandboxed IFrames](https://web.dev/articles/sandboxed-iframes) (Mike West, Google).

Sandboxing also does nothing if the untrusted content can escape into a full tab/window — a `sandbox="allow-popups"` without `allow-popups-to-escape-sandbox` is inherited by the popup, but if the site can otherwise open a full navigation, that new context isn't protected. Least-privilege is the right mental model: strip everything, add back only what the UI provably needs.

### Separate-origin iframes (`*.localhost` subdomains, blob:, srcdoc:)
- `srcdoc` content inherits the *embedding page's* origin for relative-URL resolution but is still subject to `sandbox`; it's a good mechanism to inject untrusted HTML without a network round-trip, "used as a technique to prevent script injection when displaying user-generated content, when combined with the `sandbox` attribute." [MDN iframe](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe).
- `blob:` URLs get their own opaque-ish origin tied to the creating context; fine for showing generated content without a server round trip, but not a substitute for true cross-origin isolation if the parent and child share JS realms.
- True separate-origin (a second `*.localhost` subdomain, or a dedicated user-content domain like `claudeusercontent.com`) is the pattern actually used in production — see §Claude Artifacts and §MCP Apps below. Same-origin policy is a protocol+host+port tuple; `127.0.0.1` and `localhost` and `foo.localhost` are all distinct origins to the browser, so this works for local dev too.

### Shadow DOM — explicitly NOT a security boundary
Shadow DOM (open or closed) is an *encapsulation* mechanism for component styling/markup, not an execution sandbox. A same-origin script can reach into an **open** shadow root via `element.shadowRoot`; even **closed** mode only hides the reference, it doesn't stop a script already running in that JS realm from doing anything else a same-origin script can do (read cookies, call fetch, mutate the rest of the page). The consensus among security researchers: "Shadow DOM alone cannot serve as a security boundary on normal websites... the only real option for security is to run the app inside a custom, restricted JS execution environment." [Masato Kinugawa — Shadow DOM & Security](https://speakerdeck.com/masatokinugawa/shadow-dom-and-security-exploring-the-boundary-between-light-and-shadow); corroborated by [Imperva](https://www.imperva.com/learn/application-security/shadow-dom/). If you're rendering model-generated markup into Shadow DOM in the *same document* as your app, you have gotten CSS/markup isolation, not script isolation — a malicious/buggy `<script>` in that markup still runs with your page's full privileges. Never treat Shadow DOM as a substitute for an iframe or worker boundary.

### Web Workers + remote-DOM proxying (Shopify `remote-dom`)
Shopify's `remote-dom` (formerly `remote-ui`) lets untrusted code run **off the main thread** — in a Web Worker or a sandboxed iframe — building a shadow tree of DOM-like elements that is *mirrored* into the real DOM on the host page via `postMessage`. The untrusted code never gets a live DOM reference; it only ever manipulates a serializable proxy tree that the host interprets against an allow-listed set of custom elements. [Shopify/remote-dom README](https://github.com/Shopify/remote-dom/blob/main/README.md).

Their production sandbox goes further than "just a Worker": it strips dangerous globals (`importScripts` is disabled), replaces others with safer versions (`fetch` restricted to an explicit domain allowlist), and loads the sandbox bootstrap script itself from a **separate domain** so the browser's own origin isolation backs up the JS-level restrictions. They run the same model across three platforms: Web Workers on web, WebViews on Android, JSCore on iOS. [Shopify Engineering — Remote rendering: Shopify's take on extensible UI](https://shopify.engineering/remote-rendering-ui-extensibility) (updated July 2025 to note migration to the DOM-based version).

This pattern (proxy-tree over a message channel, vetted custom-element catalog on the receiving side) is architecturally the same idea as the component-schema approach in §2, just implemented at the DOM-diff level instead of JSON-props level — worth knowing because it gives you *both* isolation (worker/cross-origin transport) *and* a bounded component surface in one design.

### CSP per isolation level
- iframe-based: the **parent** page's CSP should include `frame-src` scoped to the sandbox origin only; the **child** document gets its own CSP (`default-src 'none'` plus narrow allowances) either via response header or, per the new MCP Apps spec, synthesized dynamically from declared per-resource metadata (see below).
- Worker-based: CSP `worker-src` restricts what scripts can be loaded as a Worker; inside the worker, `fetch`/`importScripts` are the network vectors to lock down explicitly since a Worker's CSP inheritance from its parent document is a common misconfiguration point.
- All three production systems researched below converge on: **inline-only JS/CSS or worker-only execution, `connect-src`/`frame-src`/`img-src` scoped to an explicit domain allowlist supplied by the server (not the model), `object-src 'none'`.**

### What the shipping products actually do

**Claude Artifacts (Claude.ai, "Chat artifact" mode)** — runs in a sandboxed `<iframe>` served from a dedicated content origin (reported as `claudeusercontent.com`), fully isolated from the Claude.ai session: "It runs in its own isolated origin, walled off from Claude.ai itself... has no bridge to your machine: no local filesystem, no shell, no OS-level access... network and capabilities are constrained by a restrictive CSP." The CSP is strict — no external network requests, all CSS/JS must be inlined, images as data URIs, capped page size — but *does* allow `unsafe-inline`/`unsafe-eval`/`blob:` for arbitrary script execution inside that sandbox, because outbound network is what's actually blocked, not script execution itself. [Bloom Security — Inside Claude Artifacts](https://bloom.security/blog/claude-artifacts) (Jul 7, 2026).

Critically, this same source documents a **second, more powerful surface**: "Cowork" artifacts in Claude Desktop, which are NOT sandboxed the same way — every Cowork artifact shares one origin (`cowork-artifact://local`), shares `localStorage` across artifacts (a same-origin-policy violation *by design*, meaning one artifact's saved data is visible to the next), and can reach connected MCP tools (filesystem, Slack, Drive) through an injected bridge (`window.cowork`) that talks over **Electron IPC, not the network** — meaning a `connect-src: none` CSP does nothing to stop it, because the bridge doesn't route through the page's network layer at all. This is the single most important lesson in this research: **CSP governs the network; it does not govern an injected native bridge.** Any local coding-agent harness that injects host capabilities into rendered UI needs to gate the bridge itself, not rely on CSP to contain it.

**ChatGPT / OpenAI Apps SDK** — widgets run in "an isolated iframe with a strict Content Security Policy," blocked from privileged browser APIs (`window.alert`, `window.prompt`, `window.confirm`, `navigator.clipboard`), nested frames unavailable unless explicitly allow-listed per-resource via `_meta.ui.csp.frameDomains`. [OpenAI Apps SDK — Security & Privacy (official)](https://developers.openai.com/apps-sdk/guides/security-privacy). Independent reverse-engineering (["I Reverse Engineered ChatGPT Apps Iframe Sandbox"](https://dev.to/infoxicator/i-reverse-engineered-chatgpt-apps-iframe-sandbox-2ok3), by an engineer who built the first MCP-UI client in production) describes a **triple/double-iframe architecture**: an outer "sandbox proxy" iframe on a fixed origin, an inner iframe that actually loads the untrusted widget HTML, with a `localhost ↔ 127.0.0.1` origin-swap trick used in dev tooling specifically so the inner and outer frames are provably cross-origin even when both are "localhost." **[unverified — this is a third-party reverse-engineering account, not an OpenAI-published architecture diagram, though its author co-designed the now-standardized MCP Apps sandbox-proxy pattern described below.]**

**MCP Apps (SEP-1865)** — as of **January 26, 2026** this stopped being three companies' separate implementations and became **the first official MCP extension**, live in ChatGPT, Claude.ai, Goose, and VS Code, with more clients committed. [MCP Apps — Bringing UI Capabilities to MCP Clients (official MCP blog)](https://blog.modelcontextprotocol.io/posts/2026-01-26-mcp-apps/). This is the closest thing to an emerging cross-vendor consensus for exactly your use case (a coding-agent host rendering model/tool-declared UI), so it's worth describing in detail:

- A tool declares `_meta.ui.resourceUri` pointing at a `ui://` resource (bundled HTML/JS). The host fetches that resource and renders it in a **sandboxed iframe**; UI ↔ host communication is **JSON-RPC over `postMessage`**, auditable and host-validated.
- The spec's recommended web architecture is a **double-iframe "sandbox proxy"**: an outer iframe (host-controlled origin) brokers a `ui/notifications/sandbox-resource-ready` message containing the actual untrusted `html` string, a CSP object (`connectDomains`, `resourceDomains`, `frameDomains`, `baseUriDomains` — all empty by default, i.e. deny-by-default), and a `permissions` object (camera/mic/geolocation/clipboardWrite, each opt-in) into an **inner** iframe that renders the untrusted content. The inner iframe's `sandbox` attribute and CSP are synthesized server-side from that declared metadata, never author-supplied on the untrusted side.
- Named mitigations in the spec text: (1) **Iframe Sandboxing** — "the View" (untrusted UI) cannot access or manipulate the host; all communication is via host-controlled `postMessage`; (2) **Auditable Communication** — host validates all incoming RPC, rejects malformed types, logs UI-initiated calls for review; (3)/(4) not fully captured in this pass but include CSP construction from metadata (deny-by-default, explicit allowlist growth) — see the exact CSP-builder snippet in the spec.
- OpenAI's ChatGPT implementation ships **compatibility aliases** over the same wire protocol: `window.openai.toolInput`/`toolOutput`/`callTool`/`sendFollowUpMessage`/`widgetState`/`setWidgetState` map onto the portable `ui/initialize`, `ui/notifications/tool-input`, `ui/notifications/tool-result`, `tools/call`, `ui/message` primitives. [OpenAI Apps SDK — state management (official)](https://developers.openai.com/apps-sdk/build/state-management).

**Bottom line on isolation**: every production system that lets a model emit *executable code* (not just structured props) puts it behind a **cross-origin iframe**, never Shadow DOM or same-origin script alone, and the newest cross-vendor spec (MCP Apps) formalizes a double-iframe "sandbox proxy" as the reference web architecture — directly transferable to a self-hosted app.

## 2. Component-schema approach vs. code approach

**Component-schema (safe, deterministic, bounded):** the host pre-registers a catalog of vetted components with typed prop schemas (Zod/JSON Schema); the model's job is reduced to picking a component name and filling in validated parameters, streamed as JSON. Because the model is constrained to the catalog, it "cannot 'hallucinate' unsupported components, which guarantees that the generated JSON is always renderable." [Medium — Schema-Driven UIs for LLM Applications](https://medium.com/@ramu.ramaiah/schema-driven-uis-for-llm-applications-cde53e02ff02); pattern also documented at [json-render.dev](https://json-render.dev/docs/adaptive-cards).
- **Adaptive Cards** (Microsoft): a JSON schema with a `body` array of typed elements and an `actions` array, platform-agnostic, renderable across native/web hosts. [Microsoft Learn — Adaptive Cards](https://learn.microsoft.com/en-us/adaptive-cards/authoring-cards/getting-started). `json-render` explicitly integrates Adaptive Cards as one target renderer for an LLM-filled catalog.
- **JSON Forms**: schema+UISchema pair (JSON Schema for data shape, a separate UI schema for layout/renderer choice) — the same "data schema is the contract, renderer is host-controlled" idea, older and framework-agnostic (Java/TS ports exist).
- **Vercel AI SDK — Generative UI**: a tool call (`displayWeather`, defined with a Zod `inputSchema`) returns typed data; `useChat()`'s `message.parts` array carries typed `tool-${toolName}` parts with an explicit state machine (`input-streaming` → `input-available` → `output-available`/`output-error`), and your own React component renders each state — the model never emits markup, only tool-call arguments. [AI SDK UI — Generative User Interfaces (official)](https://ai-sdk.dev/docs/ai-sdk-ui/generative-user-interfaces).

**Code approach (flexible, dangerous, isolation-dependent):** the model emits actual HTML/CSS/JS (or JSX compiled client-side), and the host executes it directly. This is what Claude Artifacts and ChatGPT Canvas do — and it's exactly why they need the heavy iframe/CSP isolation from §1. The trade is expressiveness (any UI the model can imagine) for a much larger, harder-to-audit trust boundary; safety here is delegated entirely to the sandbox, not to any constraint on the content.

**2026 consensus** (converging across the sources above and the MCP Apps standardization): **use component-schema wherever the interaction is a known, bounded shape** (forms, dashboards, confirmations, structured data views) — it's cheaper to build, trivially safe, and gives you streaming-friendly partial validation for free. **Reserve full code-generation for cases that genuinely need open-ended visual/interactive expressiveness**, and when you do, put a real cross-origin sandbox under it — never render generated markup directly into your app's own DOM/origin. Several 2026 write-ups frame this explicitly as a security stance, not just an ergonomics one: keeping tool execution and raw-data handling server-side, streaming only sanitized, schema-validated UI descriptions to the client, treating "the LLM emits code" as the exception that requires its own isolation budget. [dev.to — Client-Side vs. Server-Side Tools: Generative UI Architecture](https://dev.to/programmingcentral/client-side-vs-server-side-tools-the-ultimate-guide-to-generative-ui-architecture-4hmp) **[secondary source, directionally consistent with the primary docs above but not vendor-official]**.

For a coding-agent UI specifically (your case): most of what you'd want to render — diffs, file trees, plan checklists, terminal output, confirmation dialogs — fits the component-schema model cleanly. Reach for the code-execution/iframe path only for genuinely generative visual output (e.g., the agent producing a rendered preview of a webpage it just built), which is a different, already-isolated use case (you're likely already sandboxing arbitrary preview builds separately from the chat UI itself).

## 3. Streaming: progressive rendering without flicker or broken markup

**Partial JSON / `useObject`:** Vercel's `streamObject`/`useObject` stream a Zod-validated object incrementally; the client-side hook exposes a progressively-filling `object` where "initially, object properties might be undefined, then as fields become complete enough, they appear," letting you render skeleton/placeholder states per-field rather than waiting for the whole payload. [AI SDK UI — `useObject` (official)](https://ai-sdk.dev/docs/reference/ai-sdk-ui/use-object). The SDK does the raw-model-output → structured-JSON-fragment parsing for you (JSON mode for OpenAI-style models, tool-use-based extraction for Anthropic-style models), so you're not hand-rolling a partial-JSON parser.

**Message-parts state machine:** in `useChat`, each tool invocation surfaces as a typed part with an explicit lifecycle (`input-streaming` while args are still arriving → `input-available` once args are complete/tool is executing → `output-available` or `output-error`). Your component switch-statement renders a different subtree per state — "Loading weather..." during `input-available`, the real component at `output-available`. [AI SDK UI — Generative User Interfaces](https://ai-sdk.dev/docs/ai-sdk-ui/generative-user-interfaces). This state machine is the mechanism that prevents "broken markup" flicker: you never try to render a half-formed JSON blob as if it were complete; you render an explicit incomplete-state UI until the schema says otherwise.

**Markdown/HTML streaming specifically:** the general pattern (multiple sources) is to buffer incomplete markdown and defer rendering a code block until its closing fence token has arrived, rather than re-parsing-and-re-rendering the whole message on every token — token-by-token full-message re-parses cause visible layout thrash.

**Abort:** MCP Apps' `tools/call` and the AI SDK's tool-call lifecycle are both request/response-shaped (not itself a token stream) — abort semantics for the *chat message* stream (the `AbortController`/`signal` passed into `fetch`) are separate from a mid-flight tool-UI render. The practical failure mode teams report (§5) is that aborting the outer stream without a corresponding **stream-identity check** on the UI-updating callback leaves stale renders on screen after the user has moved on.

## 4. State, persistence, and the feedback loop

**Where component state lives, and how it survives reload:** MCP Apps / OpenAI's Apps SDK draw an explicit three-way split:
1. **Ephemeral UI state** (selected tab, open panel, draft filter, not meaningful to the model) — ordinary framework state (`useState`), scoped to that one rendered instance, lost on unmount unless you persist it yourself.
2. **Widget-scoped persisted state** — `window.openai.widgetState` / `setWidgetState(state)` (portable form: not yet standardized outside ChatGPT **[unverified for other MCP Apps hosts]**). `setWidgetState` is **synchronous**, called after each meaningful UI change, and its snapshot "is persisted to the conversation and will be restored if the user navigates away and returns" — i.e., it rides along with the transcript, not a separate database. Docs explicitly warn: "do not use it as the source of truth for business data or as durable storage." [OpenAI Apps SDK — state management (official)](https://developers.openai.com/apps-sdk/build/state-management).
3. **Model-visible context** — `ui/update-model-context` (portable MCP Apps primitive): pushes a summary of what the user did in the widget into the model's context, *without* injecting it as a literal chat message the user "said."

**How user interaction feeds back to the agent — three distinct channels, not one:**
- `tools/call` (portable) / `window.openai.callTool` (ChatGPT alias) — the widget invokes another MCP tool directly, exactly like a model-initiated tool call, auditable and validated by the host the same way. Use this when a UI action should read/mutate real state (e.g., "Approve" button on a diff-review widget).
- `ui/message` (portable) / `window.openai.sendFollowUpMessage` (ChatGPT alias) — submits a message into the conversation **as if the user had typed it**, i.e. becomes a real new user turn the model will see and respond to conversationally. Use for "surface natural language interactions."
- `ui/update-model-context` — silent, out-of-band context update, no new visible turn.

This three-way split matters directly for your harness: conflating "user clicked something" with "inject a synthetic user message" is exactly the kind of design choice that later corrupts transcript replay (a synthetic message that reads oddly out of context, or a tool call that wasn't actually gated the way a model-initiated one would be).

**Session-reload / replay when transcript is the source of truth:** general pattern from persistence write-ups — full transcripts (prompts, tool calls, tool results, timestamps) are the durable record; on reopen, the client "reads the transcript history to reconstruct context, rather than resuming from an actual saved model state," and stable message/part IDs are required "to ensure consistency across sessions and prevent ID conflicts when messages are restored." **[secondary sourcing, not vendor-specific — directionally consistent with how OpenAI's widget-state-rides-the-transcript model works above]**. For an interactive component specifically, this means: if its state isn't captured in one of the three channels above (widget-state snapshot, a tool-result payload, or model context), it will not survive a reload — the component will re-mount from whatever its *last persisted tool result* was, discarding purely-client-side interaction since then.

**Pitfalls called out repeatedly across sources:**
- *Re-render loops*: syncing local `useState` to `setWidgetState` on every keystroke, then having a `useEffect` that reacts to `widgetState` changes and calls `setState` again, is a classic origin of infinite or thrashing update loops — treat the widget-state snapshot as write-mostly, not a two-way-bound store.
- *Stale closures over dead sessions*: a callback captured when the component mounted (holding an old `sessionId`/`streamId`/tool-call context) firing after the user has switched chats or the session has been torn down. The documented fix is a **"Stream Identity Guard"**: every stream/session gets a unique ID at creation, and every async callback checks "am I still the current one?" before touching state, combined with explicit cleanup (`abort()` + mark-stale on unmount) rather than relying on the component simply disappearing. [HackerNoon — Your AI Chat Will Break in Production](https://hackernoon.com/your-ai-chat-will-break-in-production-3-lifecycle-bugs-nobody-warns-you-about) (Jun 2026, healthcare-company frontend engineer, first-person production account).

## 5. Known failure modes / production lessons

1. **`allow-scripts` + `allow-same-origin` on same-origin content silently degrades to "no sandbox."** This is the single most common real-world iframe-sandboxing mistake and is called out by MDN, web.dev, and multiple WHATWG/Mozilla discussions as a recurring footgun, not a theoretical one. [MDN](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe), [Mozilla Discourse thread](https://discourse.mozilla.org/t/can-someone-explain-the-issue-behind-the-rule-sandboxed-iframes-with-attributes-allow-scripts-and-allow-same-origin-are-not-allowed-for-security-reasons/110651).
2. **CSP does not govern an injected native/IPC bridge.** Claude Desktop's "Cowork" artifacts prove this in production: a strict `connect-src: none` CSP blocks network exfiltration but not `window.cowork.*` calls that go over Electron IPC — "the usual 'just lock down the CSP' intuition doesn't fully describe what a Cowork artifact can reach." [Bloom Security](https://bloom.security/blog/claude-artifacts). Anything that injects host capabilities (filesystem, shell, other tool calls) into rendered UI must gate the bridge object itself (allowlist which calls are exposed, require explicit per-call confirmation for destructive ones), not rely on CSP.
3. **Shared origin across trust boundaries becomes a covert channel.** Same Cowork example: every artifact sharing one origin (`cowork-artifact://local`) means they all share `localStorage` — "data one artifact saves is visible to the next artifact you open." If your harness ever renders two different sessions' or two different users' generated UI under one origin, this is the exact bug class to watch for.
4. **Stream/React lifecycle mismatch.** "The stream lifecycle and the React lifecycle are two independent processes... LLM streaming is push-based... React is pull-based... If you don't synchronize them explicitly, there will be bugs. Not 'might be' — there will be." Concretely: second message sent before first finishes, user switches chats mid-stream, tab backgrounds — each breaks naive `fetch`+`setState` streaming without a stream-identity guard, explicit cleanup on unmount, and (for cache-backed stores like React Query/SWR) a forced refetch on remount rather than trusting automatic background refetch, since that stops once a query has no active subscriber. [HackerNoon](https://hackernoon.com/your-ai-chat-will-break-in-production-3-lifecycle-bugs-nobody-warns-you-about).
5. **XSS via markdown-to-HTML rendering of model output.** Model text piped through a markdown renderer can produce executable markup (`<script>`, `onclick=`, `javascript:` URLs) unless sanitized; the standard mitigation is `DOMPurify.sanitize()` on the rendered HTML before insertion, explicitly recommended as fast enough for "chat systems... where sanitization must occur instantly without noticeable delay," combined with CSP as defense-in-depth rather than a sole control. [DOMPurify docs](https://dompurify.org/how-dompurify-works-in-depth-security-and-dom-based-sanitization-explained/), [GitHub — cure53/DOMPurify](https://github.com/cure53/DOMPurify).
6. **Widget state used as a database.** Both OpenAI's docs and general practice explicitly warn against treating `setWidgetState`-style snapshots as durable/business-critical storage — it's conversation-scoped UI memory, not a database; teams that blur this line lose data on transcript truncation/summarization.

## Recommendation

**For your case — localhost-only, single-user, trusted-operator harness (a coding agent's own web UI, no remote users):**

The proportionate isolation level is: **prefer the component-schema approach for the large majority of surfaces** (diffs, plans, file trees, confirmations, run output) — it needs no iframe at all, since there's no executable content to contain, only validated JSON rendered by your own vetted React components. This gets you streaming-friendly partial rendering "for free" via `useObject`/typed message-parts and sidesteps the entire isolation question for that traffic.

**Reserve iframe sandboxing for the minority case where the agent genuinely needs to emit and execute arbitrary code** (e.g., rendering a live preview of generated HTML/JS). Even single-user-localhost, do this properly rather than skipping it: a *single* sandboxed `<iframe>` is enough — you do **not** need the full double-iframe "sandbox proxy" architecture MCP Apps specifies for multi-tenant hosts, because you have no cross-tenant confusion to defend against and no untrusted third-party MCP servers to distrust; your only adversary is the model's own generated code (XSS-style self-harm, not a malicious remote author). Concretely: `sandbox="allow-scripts"` **without** `allow-same-origin`, served with a locked-down CSP (`default-src 'none'; script-src 'unsafe-inline'; style-src 'unsafe-inline'; img-src data:; connect-src 'none'`), and no injected host-capability bridge unless a specific feature needs one — and if it does, that bridge should be an explicit, narrow, logged API (borrow the `window.openai`-style method allowlist, not a generic "call anything" bridge), because as the Cowork example shows, that bridge is invisible to CSP review.

**What changes if it later serves multiple users:** at that point, adopt the full MCP Apps-style architecture wholesale rather than reinventing it — double-iframe sandbox proxy, per-resource CSP metadata built server-side (deny-by-default `connectDomains`/`resourceDomains`/`frameDomains`), and treat every rendered UI resource as coming from a mutually-distrusting party even if it's "your own" agent, because at that point one user's session state, `localStorage`, and tool-call bridge must be provably unreachable from another's. The Cowork shared-origin/shared-localStorage design becomes a real cross-user data leak the moment there's more than one trust domain in play — that's the exact bug you'd inherit if you scaled the single-user localhost version without changing the origin model.
