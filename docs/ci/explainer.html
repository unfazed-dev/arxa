What is this page?

This page explains how changes to the arxa codebase get checked before they count as done — and how app releases are handled. arxa is the tool that builds Arxa Studio, so when its code changes, we want to be sure nothing broke before that change is accepted.

The short version: a computer checks every change the same way, every time, using one script that anyone can also run on their own machine. If it passes there, it passes in the check system.

Curious how it works under the hood? Flip the switch to — no page reload, nothing to install.

What happens when someone changes the code?

  1. They describe the change honestly. Every change summary follows a fixed wording pattern (like "fix:" or "docs:"), so the history stays readable years later.
  2. The automatic checks run. One script checks six things — the wording pattern, the change title, the project's own quality gates, the mobile app's formatting/tests, the mobile signing setup, and the transport (package delivery) code's tests.
  3. A person reviews and merges. The checks must be green first; then a human decides. Nobody can force a change past the checks.
  4. Releases stop for a human decision. Building a release is automatic; publishing it to the app stores is not. The pipeline prepares everything, then waits for a person to confirm what, which version, and from which account.

The safety checks, in plain words

  • Honest change summaries. The wording pattern is checked on every change; a vague or off-pattern summary is rejected with an explanation.
  • The app's own tests. The mobile app's code style, automatic bug detectors, and 100+ tests run on every change.
  • Signing is never faked. A real release build refuses to sign with the throwaway test key — it stops and says so, instead of quietly producing something that looks finished but isn't.
  • Nothing runs forever. Every check has a time limit, and a new update cancels the checks for the outdated one.
  • Secrets stay secret. Store credentials and signing keys are never written into the code — the system only reports whether they are present, never what they are.

Good to knowhonest trade-offs, on purpose

  • Change titles are coached, not policed. A missing stage tag in a title currently produces a friendly warning, not a rejection. It flips to strict once the habit is established — a recorded decision, not a surprise.
  • Checks run on every change, even docs-only ones. Slightly slower, deliberately: skipping checks selectively is how holes open.
  • iOS release checks need the office Mac. Apple builds only run on Apple hardware, so those lanes run on the studio's own machine. If it is asleep, iOS checks wait — that is a machine problem, never a code problem.
  • Over-the-air fixes are parked. The plumbing for pushing small app fixes without a store round-trip exists but is switched off until the plan actually needs it.

The guardrail, as a testeach line is checkable, not aspirational

  • scripts/check.sh skips cleanly when an area's code is absent — green by absence, red only when something is real
  • the commit gate excludes merge commits (git log --no-merges) — GitHub's auto-generated merge subjects false-positive a naive prefix check (measured live, energize PR #1, 2026-08-16)
  • every job declares timeout-minutes; ci.yml cancels superseded runs (mobile-release.yml deliberately does not — a half-cancelled release is worse than a slow one)
  • Android release packaging with absent signing inputs throws a clear GradleException; debug builds alone may use the debug key — pinned by test/android_release_signing_contract_test.dart and the mobile-signing area
  • a queued-but-not-running job is never "fixed" by changing code — the runner is asleep; wake it
  • renaming a job deletes its stale context from branch protection, then the protection PUT re-runs — a stale context bricks merges
  • branch protection is NOT yet applied — it goes on only after the first green run is watched (docs/ci/setup.md first-green checklist)
