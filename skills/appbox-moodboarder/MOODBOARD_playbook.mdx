# appbox-moodboarder — Per-Skill Playbook

`appbox-moodboarder` · status: **active**

**Role (one line):** turn a story map into a scored, selected, and auditioned moodboard of real reference apps — one gathering subagent per epic, key screens captured with the appbox lens, boards under `<app-dir>/moodboard/`, scored against the intake rubric, human-selected, then synthesized into three suitors of which the human picks one.

**Scope of this document:** lets a human OR an LLM run a moodboard pass without reading the skill source. Folded from `SKILL.md`.

**Pipeline position:** stage 0 — upstream `appbox-story-mapper` (`story-map.json`); downstream `appbox design commission` (refuses until the selection is approved and, on new-style records, a suitor is chosen); captures and measured evidence via `appbox-lens`. Full chain, stage numbers, per-stage artifacts: `docs/research/pipeline-map.md` §1.

### Overview & role

The moodboarder elicits **visual direction** the way the story-mapper elicits scope: it gathers, captures, scores, and synthesizes; it does NOT design (architecture §22). It runs after `appbox-story-mapper` and before `appbox-designer`. The designer consumes ONLY the compiled commission — never the raw boards — which is why every gate below exists: an unfed, unselected, or unauditioned board starves the mandate silently.

### Inputs

`docs/intake/story-map.json` — sliced one gathering slice per epic (per feature when an epic holds 3+ features); the stories each slice must satisfy anchor every reference's "why it fits". The intake rubric comes from `intake/answers.json` + `intake/direction.json`: each direction adjective → criterion (weight 1); an adjective naming a concrete visual requirement (motion, 3D, animation, video) → `locked: true`, weight 3; `layoutTemplate` → weight 2; each avoid → scored inverted.

### Procedure

1. **Gather** — dispatch one subagent per slice, in parallel (one message, ≤8), on the SKILL.md prompt template: 6–10 shipping apps, concrete screens/patterns to steal and why they fit, 1–3 key screens each (publicly reachable, nothing behind login), freshness graded 🔥/🌡️/❄️.
2. **Capture** — `dart run appboxd/tool/lens_shot.dart <url> <out.png> [w h settle] [--full]` to `<app-dir>/moodboard/shots/<slice-slug>/<ref-slug>__<screen-slug>.png` (device viewports when references inform a full-parity app; 3000–3500ms settle for animation-heavy references).
3. **Assemble** — `<app-dir>/moodboard/boards/<slice-slug>.md` per the assembly format, ending with the top-10 "Patterns this slice must have", each traceable to a reference. Verify with the runnable resolver (below); zero MISSING lines = pass.
4. **Score** — every reference 0–5 per criterion; judgment is the subagent's, arithmetic is the CLI's (`appbox moodboard check` recomputes Σ(score×weight)/Σweight). **Locked criteria are scored on proof, not recall**: a score ≥ 3 on a locked criterion cites lens evidence on the reference's `evidence` list (two settle-state captures that differ, burst frames, a recorded probe — files under `moodboard/evidence/…`); an unreachable reference scores ≤ 2 on the lock.
5. **Record** — write the `moodboard` answer group into `intake/answers.json` (`provenance`, `criteria`, `boards` with scores, `selectionStatus: "pending"`), re-run the intake emitter, then `appbox moodboard check <intake-dir>` — green required.
6. **Selection gate (human)** — present each board's references ranked by weighted total (default proposal: every reference ≥ 3.5); the founder picks. Record `selected: true`, set `selectionStatus: "approved"`, re-emit, re-check.
7. **Suitors — the direction audition (human)** — synthesize exactly three candidate directions (A, B, C) from the SELECTED set only: name, lead references (`<boardId>/<reference name>`), cross-pollination attribution, spread statement, tokens lens-measured where reachable (`appbox lens tokens`; motion via two settle states / burst) with `provenance: measured|judged`. If the set yields one direction, STOP and surface the finding. Present; the founder names one primary plus optional attribute-scoped remix clauses (`palette`, `type`, `radius`, `motion`, `layout-register` — "B, but motion from C" is complete). Record `suitors` + `suitorChoice`, re-emit, re-check.
8. **Hand off** — `appbox design commission <app-dir>` compiles the mandate: selected references only, the chosen suitor (+ remixes) as the token spine; it REFUSES while the selection is unapproved or (new-style) no suitor is chosen.

### Outputs

`<app-dir>/moodboard/boards/<slice-slug>.md` + `shots/<slice-slug>/…png` + `evidence/…`; `intake/moodboard.json` (emitted, with computed totals, `suitors`, `suitorChoice`); then `design/commission.md` + `commission-prompt.md`. Legacy records (pre-audition, energize included) stay valid under the law of their day — the gates apply from their landing.

### Rules

Skip and note screens behind auth; never capture with credentials. A failed capture is recorded as `_(capture failed: reason)_` — never a hotlinked URL silently substituted. The verify step resolves every embedded path on disk — an asset check that verifies strings instead of resolving paths is this project's recurring green-gate defect. Plain shots, measured tokens, and motion proofs only here: golden compares, console gates and native captures belong to the build visual gates. The lens's isolation (own headless Chrome per run) makes parallel slice capture safe with no env juggling.
