# appbox-scaffolder — Per-Skill Playbook

`appbox-scaffolder` · status: **active**

**Role (one line):** turn a FROZEN `structure.json` + target set into the per-surface Flutter file set the coverage gate asserts — form factors follow targets, never empty.

**Scope of this document:** lets a human OR an LLM drive the scaffold engine without reading the skill source. Folded from `SKILL.md`.

### Overview & role

The scaffolder PRODUCES the tree the gates ASSERT (architecture §16). The structure gate checks the authored layer against `structure.json`; the coverage gate checks the scaffolded layer against `structure.json` + targets. This skill is the missing producer between them — the one the P14 dogfood named (14.8 / honest-bar #2): until it existed, no tool turned a frozen design into the Flutter file set, so "scaffold D1" and "coverage of D1" had no target. It is the inverse of the structure gate: where that gate asserts the tree matches the registry, the scaffolder emits that tree. It emits STRUCTURE only — minimal valid Dart skeletons carrying the class name the builder (plan 08) implements; the widget bodies are not this skill's concern.

### Inputs

- A **frozen** `structure.json` at `<design-dir>/structure.json` (produced by `tools/emit_structure`; the scaffold reads it as frozen input and never re-derives structure).
- A **target set** (`--targets macos`, or `ios,android`, or `web`, …) — explicit, never ambient. Every target must have an entry in `pipeline/state/targets.derivation.json`.
- The derivation table (`pipeline/state/targets.derivation.json`) and config viewports (`config/appbox.config.json`) — the source of factor names and ordering (P06/R3). The scaffold reads these; it does not hardcode them.

### Procedure

Confirm the design is frozen (`appbox emit structure --check` in sync). Scaffold, naming targets explicitly: `appbox emit scaffold --design-dir <design> --app-root <app> --targets macos` (the Dart port of the archived `scaffold.py`). `--targets` is required (or `APPBOX_TARGETS` env); the scaffold never reads ambient pipeline state for targets (the stale-green defect, §16). Widths and factor names come from the derivation table + config, never literals (R3). Verify drift after a registry edit with `--check`: it regenerates the expected set in memory and diffs against disk, naming any missing factor file, stale manifest, or hand-edited dir — the same file set `gates/coverage` (C1) walks. Hand the scaffolded tree to `appbox-builder` for the widget bodies; the coverage gate then asserts the scaffolded layer.

### Outputs

Per frozen surface (those with `surface` non-null in `structure.json`), under `<app-root>/lib/ui/views/<shellDir>/<shell>_<short>/`: `_view.dart` + one `_view.<factor>.dart` per **derived** factor + `_viewmodel.dart`. `macos` → 3 files/surface (desktop only); `ios,android` → 4 (mobile+tablet); `web` → 5. Excluded surfaces (`surface:null`) are not scaffolded. Plus `lib/ui/views/.shell-structure.json` — the manifest the coverage gate reads (`selfContained` + the `{shellDir: {surfaceId: dir}}` map). The directory name is `<shell>_<short>` from the registry id (the stable key, §18), recorded because the coverage gate refuses to guess it.

**l10n layer (optional):** when the design carries `l10n/app_<locale>.arb` catalogs, they are copied verbatim into `lib/l10n/`, a fixed-contract `l10n.yaml` (`arb-dir: lib/l10n`, `template-arb-file: app_en.arb`, `nullable-getter: false`) is written at the app root, and the manifest gains `"l10n": {"arbDir": "lib/l10n", "locales": [...]}` for gates to read. `--check` asserts the catalog file set + `l10n.yaml` match the design. A design without `l10n/` emits no l10n artifacts (backward compat). A missing `app_en.arb` template fails loudly — the yaml contract is fixed.

### Rules

Form factors follow targets — never emit an empty `.mobile`/`.tablet` to satisfy a count; that is the stale-green pattern §16 exists to kill (the self-test guards it). Never hardcode widths or factors — they come from the derivation table + config (P06/R3); adding a target is a data edit, not a code change here. Never read targets from ambient state — pass `--targets` explicitly. Never edit scaffolded Dart directly — edit the authored layer, re-freeze, re-scaffold, or the drift check dies. Treat stub bodies as unfinished — the builder replaces them. Keep `appbox emit scaffold --self-test` (and `appboxd/test/scaffold_test.dart`) green when you change the engine; it is the proof the guardrail holds (negatively: missing structure.json, surface with no viewmodel, wrong file count, unknown target, dir collision; positively: macos→desktop only with no empty factors).

### Emitted file structure (semantic frontmatter)

Every scaffolded file starts with `library;` and a placeholder `///` doc comment that the builder fills in. The stub is a skeleton; the builder replaces the placeholder with the full five-part spine (layer intro → role paragraph → requirements → relationships → history) per `BUILDER_playbook.mdx → File structure`.

**Per-kind stub headers (what the scaffold emits):**

- **ViewModel:** `/// <Layer intro: actions in, streams out, never touches the view>` + `library;` + imports + `class … extends AppBoxKitViewModel { // ── Setup ── }`
- **View:** `/// <Layer intro: composes primitives, binds VM streams>` + `library;` + imports + class
- **Widget:** same pattern as view.
- **Service (facade/adapter/repository):** `/// <Role opener: front door / bridge to device / store>` + `library;` + imports + class.
- **Model:** `/// <Role paragraph>` + `library;` (light variant — no diagram).

**Body section markers (locked order per kind):**

| Kind | Separators |
|---|---|
| viewmodel | `// ── Setup ──` / Initial state / Streams / Commands / Actions / Side effects / Cleanup |
| facade | `// ── Setup ──` / Initial state / Streams / Writes / Reads / Cleanup |
| adapter | `// ── Setup ──` / Initial state / Streams / Actions / Cleanup |
| repository | `// ── Setup ──` / Reads / Writes / Cleanup |
| views/widgets | no invented sections — natural build order |

The scaffold emits only the `// ── Setup ──` marker in the stub; the builder adds the rest as it fills the body. Empty sections are omitted — a VM with no hub commands has no Commands section.

See `skills/appbox-builder/BUILDER_playbook.mdx → File structure (semantic frontmatter)` for the full grammar, and `kit/showcase_app/.../showcase_note_editor_viewmodel.dart` for the reference implementation.
