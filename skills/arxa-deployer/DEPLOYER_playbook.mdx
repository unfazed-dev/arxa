# arxa-deployer — Per-Skill Playbook

`arxa-deployer` · status: **active**

**Role (one line):** ship an arxa-built target to stores (fastlane), push an OTA Dart patch (shorebird), and/or deploy a web build to Cloudflare Pages/Workers or Vercel — all behind the strictest human gate.

**Scope of this document:** lets a human OR an LLM drive the deploy phase without reading the skill source. Folded from `SKILL.md`.

**Pipeline position:** stage 9, the chain's end — upstream `arxa-reviewer` (GREEN verdict) + the `native_deps` packaging gate; `arxa-cicd`'s deploy job halts at this skill's HUMAN GATE 3. Full chain, stage numbers, per-stage artifacts: `docs/research/pipeline-map.md` §1.

### Overview & role

fastlane, shorebird and wrangler are existing CLIs; this role drives them with a recipe. The Fastfile, `shorebird.yaml` and Pages project are operator-owned extension points — signing, bundle id, app ids and the Pages project name are project secrets the pipeline never holds. The mechanics live in `arxa/lib/deploy.dart` (the Dart port of the former `deploy.py`, now archived): every external CLI runs through a `ProcessRunner` port, so `arxa deploy --self-test` asserts each command shape under a scripted runner with no toolchain, no credentials and no signing identity.

**Targets — wired (honest about verification tier):**

| target | status |
|---|---|
| `fastlane-ios` / `fastlane-android` | wired |
| `shorebird-release` / `shorebird-patch` | wired |
| `cloudflare-pages` | wired |
| `cloudflare-workers` | wired (port-tested) |
| `vercel` | wired (port-tested) |

All five are surfaced to an operator. `vercel` and `cloudflare-workers` are port-tested tier: command shapes pass under the scripted runner, but neither is CI-verified against a real project yet — `gates/advertise` caps any offer at the tier recorded in `config/kit-registry.json`.

### Inputs

- A released target (reviewer-green) at `<target>/`.
- Operator-owned signing (`match`), bundle id, team, store keys, shorebird app id, Cloudflare Pages project/token — never committed.
- The confirmed deploy triple in pipeline state (`approvalTokens.deploy`: version + account), asserted by `gates/deploy`.

### Procedure

**Stores — fastlane (gym + match + deliver/supply):** once per project, `fastlane init` in `<target>/ios` + `<target>/android`; operator fills signing. Beta lane `fastlane beta`: iOS `gym`→`match`→`upload_to_testflight`; Android `flutter build appbundle`→`upload_to_play_store(track: internal)`. Release lane `fastlane release`: store metadata (`deliver`/`supply`) + production track.

**OTA — shorebird:** once, `shorebird init` → `shorebird.yaml`; patch with `shorebird release patch` after a Dart-only fix (catches the 80% logic-bug case without a store round-trip). Boundary: shorebird patches Dart only (bug fixes, not features); native changes → fastlane full release.

**Web — Cloudflare Pages:** once, `wrangler pages project create <name>` (operator-owned); deploy with `wrangler pages deploy <dir> --project-name <name>`, which returns a deployment URL.

**Web — Cloudflare Workers:** `wrangler deploy` in the worker directory, with `CLOUDFLARE_API_TOKEN` + `CLOUDFLARE_ACCOUNT_ID` in the ambient environment; returns a deployment URL.

**Web — Vercel:** `flutter build web --release`, then `vercel deploy build/web --prod --yes` with `VERCEL_TOKEN` in the ambient environment (`VERCEL_ORG_ID` / `VERCEL_PROJECT_ID` to link non-interactively); returns a deployment URL.

**The gate.** Deploy is the third human gate and the strictest — it is a write to the outside world that cannot be undone by re-running a stage. `gates/deploy` names target + version + account and requires a person to confirm that exact triple. Run `doctor` as preflight (it reports readiness; it is NOT the gate). An agent may prepare, preflight, reach the gate and stop — it never mints the approval token. `arxa deploy deploy` requires that approval as an argument and halts without it, recording a `halted` ledger row.

### Outputs

A shipped build (store track), a shorebird patch version, and/or a web deployment URL (Pages, Workers or Vercel). Every attempt — shipped or halted — is recorded in the deploy ledger (`pipeline/state/deploy-ledger.json`, overridable via `ARXA_DEPLOY_LEDGER`): target, version, account, approving person, timestamp, resulting artefact id. Deploy is the only outward-facing pipeline action — confirm with the operator before pushing.

### Rules

Never commit secrets — `.env`, signing, store keys, the Cloudflare tokens and `VERCEL_TOKEN` are operator-owned, gitignored. Release is gated on QC green + manifest hash match; don't ship a drifted target. The pipeline stamps `0.1.0+1` in the generated pubspec; the operator bumps per release. Offers are capped at each provider's verification tier in `config/kit-registry.json` — `vercel` and `cloudflare-workers` are port-tested, not yet CI-verified.
