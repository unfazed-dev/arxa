Glass surfaces now default to *opaque*: `ArxaKitGlassCard`, `ArxaKitNativeInputBar`, and the dialog surface (both `arxaKitShowNativeDialog` and the widget) all take `opaqueGlass` defaulting to **true**, painting a flat opaque base behind the content; pass `opaqueGlass: false` for the old fully transparent backing. Sheets are the exception worth reading twice — `arxaKitShowNativeSheet(opaqueGlass:)` defaults to **true**, but the raw sheet widget's own field defaults to **false**, so direct widget construction is transparent unless you say otherwise. ### Usage & wiring

Add `arxa_kit_ui_library` as a path dependency and import the single barrel `package:arxa_kit_ui_library/arxa_kit_ui_library.dart` — it re-exports `arxa_kit_core`, so widgets, tokens, the arxaKitLocator, and the error/theme services all arrive through one import. The barrel also re-exports the arxa-mandated framework surface — `stacked` (+ `stacked_annotations`), rxdart's `BehaviorSubject`/`ValueStream`/`Rx`/`SwitchMapExtension`, and the stacked_services config types (`RouterService`, `SnackbarService`, `SnackbarConfig`, `SnackPosition`, `StackedService`) — so app pubspecs never declare those packages. At boot, call `setupLocator()` (registers `ArxaKitNotificationService` and the rest), then `setupArxaKitUiServices()` (DialogService / SnackbarService / BottomSheetService-as-ArxaKitBottomSheetService / Talker — keeps those registrations, and their packages, out of app code), then `setupKitSnackbars()` to install the `SnackbarConfig` variants the Android and iOS-action-fallback tiers render. Mix `ArxaKitPlatformPagesMixin` into your generated `AppRouter` (which already extends `StackedRouterWeb`) to render Cupertino pages on iOS and Material pages elsewhere. Widget call sites take primitives only — e.g. `ArxaKitNativeButton(onPressed: ..., label: 'Save', glyph: ArxaKitGlyphs.save)` — and operations flow through the fluent `action(name, () => ...).withLoading(...).withSnackbars(...)` API (the builder is awaitable — awaiting it executes the operation).

All transient UI goes through `ArxaKitNotificationService` — the kit-rendered verbs mean apps never register stacked dialog/sheet variants for the generic cases: `show(...)` (toast/snackbar, platform-routed), `confirm(title, ...)` → `bool` (cancel/barrier → false), `prompt(title, ...)` → trimmed `String?` (cancel/empty → null), `alert(title, ...)` (single action), `notice(title, message)` (modal sheet via `arxaKitShowNativeSheet`). Dialogs/sheets render through `arxaKitShowNativeDialog`/`arxaKitShowNativeSheet` (frosted iOS tier, M3 elsewhere); ArxaKitAction's `dialog`/`bottomSheet` notification types route through `alert`/`notice` too. Tests use `FakeArxaKitNotificationService` (records every verb; `confirmResult`/`promptResult` script the answers).

Repo-level consumer map: `ui-library-usage-appendix.md` in this package (SSOT) catalogues every barrel symbol and where it is used across the host app, the tests, the showcase app, and the other kit packages.

### Architecture

`arxa_kit_ui_library` sits in the single tier above core — its only kit edge is `arxa_kit_ui_library → arxa_kit_core`, which it re-exports so consumers need one import. The `Kit*` widgets are adaptive **ports**: each takes primitives (labels, SF Symbol names, `ArxaKitGlyph` tokens) and delegates to a vendored fork for the native render — `ArxaKitNativeButton`/`ArxaKitNativeAppBar` route to `cupertino_native_better` (real Liquid Glass on iOS/macOS 26+, Cupertino below, Material on Android/web), while `ArxaKitNativeFab`, `ArxaKitNativeNavigationRail`, `ArxaKitNativeSplitButton`, `ArxaKitNativeTextField`, and `ArxaKitNativeToolbar` delegate to their `*_m3e` forks. The UI-coupled services (`ArxaKitNavigationControllerService`, `ArxaKitBottomSheetService`, `ArxaKitNotificationService`) are drop-in stacked `StackedService` subclasses resolved through `arxaKitLocator`, and `ArxaKitAction` is a static facade composing managers (error/loading/notification/stream/success) with executors behind a fluent builder. No widget or service reaches for a plugin type directly — native tiers live behind the port, so the kit ships genuine native chrome with no native code of its own.


### Gotchas

Native setup lives in the host, not the kit: Android predictive back requires `enableOnBackInvokedCallback=true` in the manifest, and every `cupertino_native_better` hosted view must opt out of safe-area regions (`UIHostingController` platform views otherwise compress on fling). On iOS the notification tier is fire-and-forget `CNToast` by default — passing an `actionLabel` is the *only* thing that promotes it to a snackbar, so never assume a snackbar renders on iOS. `ArxaKitBottomSheetService` preserves the stacked API but silently ignores Get-specific knobs (`enableDrag`, enter/exit durations, `useRootNavigator`, `elevation`), and `isBottomSheetOpen` still reads Get state and will report `false` for kit-presented sheets. Maintenance risk is concentrated in `vendor/` — the six forks (`cupertino_native_better`, `fab_m3e`, `navigation_rail_m3e`, `split_button_m3e`, `text_field_m3e`, `toolbar_m3e`) carry their own tests and must be re-verified on iOS SDK bumps; stacked 3.5.0's `AdaptivePage` is material-on-all-platforms, which is exactly why `ArxaKitPlatformPagesMixin` exists.

ArxaKitAction ops are owner-keyed via the `ArxaKitActionOwner` mixin (`ArxaKitViewModel`, `ArxaKitDataFacade`, adapters/services `with ArxaKitActionOwner`) — keys derive as `RuntimeType#identityHash.name` (`ArxaKitAction.deriveKey`), never hand-written. **The hub is the app-level API**: `abxActionHub.on<P, R>('name', (payload) => ..., errorMessage:, withValue:, errorNotification:, successNotification:, loadingNotification:, *NotificationType:, onError:, onSuccess:, onSend:, debounce:, throttle:, parallelExecution:, flushOnDispose:, retry:, timeout:, confirmTitle:, confirmMessage:, confirmActionLabel:, confirmDestructive:)` registers one hot command channel per op, and `command.send(payload)` ALWAYS executes — it returns `Future<R>`, an *observation handle* on the already-running op (async_redux dispatch/dispatchAndWait model): awaiting is optional, dropping is harmless (handle errors are pre-observed, never unhandled). A send while the same key is in flight never re-runs — its handle completes with the in-flight run's result, never a guard error (`parallelExecution: true` opts out: every send runs, each handle gets its own result). Debounce-superseded handles complete with the eventual run's result (debounce drops events, not callers); throttle is leading-edge with the window anchored at the last run's START (throttled-away handles observe the in-flight/previous run). `errorMessage` is completeOnError parity (swallow + `withValue` fallback; without it the handle completes with the original error), `onError`/`onSuccess` are the handleError/onSuccess taps (onSuccess awaited after the op, before the success notification and handle completion; tap errors only warn), `loadingNotification` fires at run start, and the notification params route to snackbar (default) or the kit-rendered alert/notice surfaces (dialog/bottomSheet types). `confirmTitle:` gates the run on ArxaKitNotificationService.confirm — a decline never executes the op (no busy state, no notifications) and the handle completes with `withValue`. Dispose cancels subs then subjects; pending debounced sends complete with a disposed error UNLESS the command set `flushOnDispose: true`, which executes them immediately (attaching to an in-flight run per guard semantics) — `dispose()` returns a `Future` that awaits those flushes, and in-flight ops always run to completion: cancellation is cooperative-only, Dart futures cannot be aborted. The `pipeline` getter is lazy (override `createPipeline()` for owner-wide defaults) and dies with `disposeArxaKitActions()` — which `ArxaKitViewModel.dispose` calls, so no manual wiring. Need real mid-flight cancel, `toStream`, or progress callbacks? The **low-level builder** (`action(name, () => ...)` / `ArxaKitAction.run`) is LAZY (an un-awaited chain never runs — exactly the footgun pipes exist to kill) and stays in kit only for those forms; app code should not use it — note its `withProgress` is dead config (no executor ever invokes it), there is no progress concept to port. Op busy/error state is a stream either way: `vm.actionState$('name')` (pipe and builder share the derived key and the state manager) bound in views via `ArxaKitStreamBuilder`. `watch(name, streams:, callback:)` takes any `Stream` and its callback receives the emitted value — it is for VM-internal side effects, never view data (views bind streams directly); compose dependent subscriptions with rxdart `switchMap` into one stream instead of nesting listeners. Any code path that can hit ArxaKitAction's error handling needs `ArxaKitErrorService.initialize()` called at boot first (late Talker), and widget-less tests must register `FakeArxaKitNotificationService` under the explicit `ArxaKitNotificationService` type or the real CNToast path dies on the missing navigator context.

Liquid-glass surfaces *inside a scrollable under pinned chrome* ghost on iOS: the compositor's native clip chain is the only thing occluding a `UiKitView` during scroll and it is historically unreliable (flutter #25965/#76097/#154664; `BackdropFilter` glass joins the artifact class via #175048). Wrap any `CN*`-backed widget or `ArxaKitGlassCard` that lives in a `CustomScrollView` in `ArxaKitScrollOcclusionGate` (or the `.scrollOcclusion()` extension) — proportional fade to alpha 0 detaches the native layer by full coverage; `ArxaKitNativeChromeGate` is the *modal-depth* sibling and composes with it. Reviewer check 1i enforces the pairing; full mechanism in `core/NATIVE_COMPONENTS.md` ("Scrolled under pinned chrome").

The bottom-edge scrim is a `LinearGradient` with per-stop alpha, never an `Opacity` and never a `BackdropFilter` band — a blur band cannot sample platform-view pixels (they punch through) and an alpha wrapper is the forbidden mutator over native glass, so the gradient is the only lawful way to keep scrolled content from hard-clipping at the physical bottom edge. Toasts mount on `Overlay.maybeOf(ctx, rootOverlay: true)` so the pill outranks every surface in the app — a non-root overlay puts it *under* sheets and dialogs. Chrome hiding routes through `ArxaKitNativeChromeGate`: `ArxaKitChromeHideMode.keepAlive` is the default and hides at *paint* level (the child stays mounted behind an `IndexedStack` whose index selects an empty placeholder, so layout, state, and semantics survive), with `unmount` as the explicit opt-out. Prefer the gate over hand-rolled conditional chrome — see `docs/liquid-glass-allowlist.md` for which surfaces travel with a transition.


### Testing

Tests never touch platform channels — services are exercised by hand-written recording stubs registered into `arxaKitLocator` before the call. The canonical pattern (see `test/kit/services/arxa_kit_notification_service_test.dart`) is a `_RecordingSnackbarService` whose `showCustomSnackBar` override increments `calls` and captures `lastMessage`, `lastVariant`, `lastDuration`, and `lastActionLabel`; assertions then check `expect(svc.calls, 1)` plus the mapped variant and forwarded fields. Platform branches are forced with `ArxaKitPlatform.override` (e.g. `ArxaKitPlatformOverride(isAndroid: true)`) so the Android-vs-iOS tier split is deterministic on the macOS test host. The `CNToast` tier is fire-and-forget and paint-unasserted — its test asserts the *negative* (`SnackbarService` NOT invoked) to lock the de-mix contract rather than the toast pixels.

### Decisions / ADRs

`arxa_kit_ui_library` is the one kit permitted to depend on `arxa_kit_core` — the matrix's star topology makes `kit → core` the only allowed kit edge (discouraged for capability kits but required here because the UI tier is genuinely MVVM-coupled). It is deliberately **not** standalone: it owns the Stacked-coupled surface (router pages, `BottomSheetService`/`SnackbarService` subclasses, arxaKitLocator resolution) that capability kits are kept free of. The six vendored forks were folded in (ADR-0002, relocate-vendor) rather than consumed from pub.dev because each carries a fix upstream ignores — `navigation_rail_m3e` repairs the unclipped expand overflow and indicator-corner sync, `cupertino_native_better` is the only path to real Liquid Glass on iOS 26+, and `ArxaKitPlatformPagesMixin` exists because stacked 3.5.0's `AdaptivePage` builds a material route on every platform and never attaches the iOS edge-swipe gesture. Vendoring trades a maintenance debt (re-verify on iOS SDK bumps) for genuine native chrome with no native code in the kit itself.

The 2026-08-13/14 glass rulings changed three defaults: edge treatment is on for both edges rather than opt-in, the dialog/input-bar/card glass surfaces paint an opaque base rather than a transparent one, and chrome hiding is a paint-level gate that keeps the child mounted rather than a widget-tree removal. Rationale for all three lives in `docs/liquid-glass-allowlist.md` — THE liquid-glass law, and the SSOT for *why*; this playbook only indexes the resulting API.
