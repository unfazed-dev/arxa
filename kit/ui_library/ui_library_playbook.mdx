### Usage & wiring

Add `ui_library` as a path dependency and import the single barrel `package:ui_library/ui_library.dart` — it re-exports `appbox_kit_core`, so widgets, tokens, the locator, and the error/theme services all arrive through one import. At boot, call `setupLocator()` (registers `KitNotificationService` and the rest) followed by `setupKitSnackbars()` to install the `SnackbarConfig` variants the Android and iOS-action-fallback tiers render, and register `KitBottomSheetService` as the base type (`LazySingleton(classType: KitBottomSheetService, asType: BottomSheetService)`) so stacked sheet call sites stay untouched. Mix `KitPlatformPagesMixin` into your generated `AppRouter` (which already extends `StackedRouterWeb`) to render Cupertino pages on iOS and Material pages elsewhere. Widget call sites take primitives only — e.g. `KitNativeButton(onPressed: ..., label: 'Save', glyph: KitGlyphs.save)` — and operations flow through the fluent `KitAction.run<T>(operation: ...).withLoading(...).withSnackbars(...).execute()` API.

Repo-level consumer map: `ui-library-usage-appendix.md` in this package (SSOT) catalogues every barrel symbol and where it is used across the host app, the tests, the showcase app, and the other kit packages.

### Architecture

`ui_library` sits in the single tier above core — its only kit edge is `ui_library → appbox_kit_core`, which it re-exports so consumers need one import. The `Kit*` widgets are adaptive **ports**: each takes primitives (labels, SF Symbol names, `KitGlyph` tokens) and delegates to a vendored fork for the native render — `KitNativeButton`/`KitNativeAppBar` route to `cupertino_native_better` (real Liquid Glass on iOS/macOS 26+, Cupertino below, Material on Android/web), while `KitNativeFab`, `KitNativeNavigationRail`, `KitNativeSplitButton`, `KitNativeTextField`, and `KitNativeToolbar` delegate to their `*_m3e` forks. The UI-coupled services (`KitNavigationControllerService`, `KitBottomSheetService`, `KitNotificationService`) are drop-in stacked `StackedService` subclasses resolved through `locator`, and `KitAction` is a static facade composing managers (error/loading/notification/stream/success) with executors behind a fluent builder. No widget or service reaches for a plugin type directly — native tiers live behind the port, so the kit ships genuine native chrome with no native code of its own.


### Gotchas

Native setup lives in the host, not the kit: Android predictive back requires `enableOnBackInvokedCallback=true` in the manifest, and every `cupertino_native_better` hosted view must opt out of safe-area regions (`UIHostingController` platform views otherwise compress on fling). On iOS the notification tier is fire-and-forget `CNToast` by default — passing an `actionLabel` is the *only* thing that promotes it to a snackbar, so never assume a snackbar renders on iOS. `KitBottomSheetService` preserves the stacked API but silently ignores Get-specific knobs (`enableDrag`, enter/exit durations, `useRootNavigator`, `elevation`), and `isBottomSheetOpen` still reads Get state and will report `false` for kit-presented sheets. Maintenance risk is concentrated in `vendor/` — the six forks (`cupertino_native_better`, `fab_m3e`, `navigation_rail_m3e`, `split_button_m3e`, `text_field_m3e`, `toolbar_m3e`) carry their own tests and must be re-verified on iOS SDK bumps; stacked 3.5.0's `AdaptivePage` is material-on-all-platforms, which is exactly why `KitPlatformPagesMixin` exists.

Liquid-glass surfaces *inside a scrollable under pinned chrome* ghost on iOS: the compositor's native clip chain is the only thing occluding a `UiKitView` during scroll and it is historically unreliable (flutter #25965/#76097/#154664; `BackdropFilter` glass joins the artifact class via #175048). Wrap any `CN*`-backed widget or `KitGlassCard` that lives in a `CustomScrollView` in `KitScrollOcclusionGate` (or the `.scrollOcclusion()` extension) — proportional fade to alpha 0 detaches the native layer by full coverage; `KitNativeChromeGate` is the *modal-depth* sibling and composes with it. Reviewer check 1i enforces the pairing; full mechanism in `core/NATIVE_COMPONENTS.md` ("Scrolled under pinned chrome").


### Testing

Tests never touch platform channels — services are exercised by hand-written recording stubs registered into `locator` before the call. The canonical pattern (see `test/kit/services/kit_notification_service_test.dart`) is a `_RecordingSnackbarService` whose `showCustomSnackBar` override increments `calls` and captures `lastMessage`, `lastVariant`, `lastDuration`, and `lastActionLabel`; assertions then check `expect(svc.calls, 1)` plus the mapped variant and forwarded fields. Platform branches are forced with `KitPlatform.override` (e.g. `KitPlatformOverride(isAndroid: true)`) so the Android-vs-iOS tier split is deterministic on the macOS test host. The `CNToast` tier is fire-and-forget and paint-unasserted — its test asserts the *negative* (`SnackbarService` NOT invoked) to lock the de-mix contract rather than the toast pixels.

### Decisions / ADRs

`ui_library` is the one kit permitted to depend on `appbox_kit_core` — the matrix's star topology makes `kit → core` the only allowed kit edge (discouraged for capability kits but required here because the UI tier is genuinely MVVM-coupled). It is deliberately **not** standalone: it owns the Stacked-coupled surface (router pages, `BottomSheetService`/`SnackbarService` subclasses, locator resolution) that capability kits are kept free of. The six vendored forks were folded in (ADR-0002, relocate-vendor) rather than consumed from pub.dev because each carries a fix upstream ignores — `navigation_rail_m3e` repairs the unclipped expand overflow and indicator-corner sync, `cupertino_native_better` is the only path to real Liquid Glass on iOS 26+, and `KitPlatformPagesMixin` exists because stacked 3.5.0's `AdaptivePage` builds a material route on every platform and never attaches the iOS edge-swipe gesture. Vendoring trades a maintenance debt (re-verify on iOS SDK bumps) for genuine native chrome with no native code in the kit itself.
