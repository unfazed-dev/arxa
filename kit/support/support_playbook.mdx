### Overview & role

In-app support port for appbox_kit apps — screenshot+annotation feedback flow (feedback package) bundled with an injected Talker log export, routed to a swappable submission sink (local-file export by default). Standalone; no appbox_kit core dependency.

### Usage & wiring

- Wrap the app in **`BetterFeedback`** at the root (from the `feedback`
  package) — `startFeedbackFlow` requires that ancestor.
- `feedback`'s screenshots need Flutter's **CanvasKit renderer** on web, and
  platform views (maps, webviews) render blank in the screenshot.
- `AppBoxKitLocalFileSubmissionSink` uses `dart:io`; on web, inject a
  `AppBoxKitCallbackSubmissionSink` instead.

### Architecture

`AppBoxKitSupportService` is the single entry point and depends only on two things it is handed: the app's already-registered `Talker` instance (injected, never constructed here) and a `AppBoxKitSubmissionSink`. `AppBoxKitSubmissionSink` is the port — an abstract `submit(AppBoxKitFeedbackSubmission)` — that the concrete adapters (`AppBoxKitLocalFileSubmissionSink`, `AppBoxKitCallbackSubmissionSink`, plus the `AppBoxKitEmailSubmissionSink` / `AppBoxKitGithubIssueSink` stubs) implement, so the service is transport-agnostic. Dependency direction runs one way: service → port → the immutable types in `appbox_kit_support_types.dart` (`AppBoxKitDiagnosticsBundle`, `AppBoxKitFeedbackSubmission`, `AppBoxKitSubmissionResult`), and the sinks depend on those same types rather than back on the service. No edge points at `appbox_kit` core, `stacked`, or `stacked_services`.


### Gotchas

`startFeedbackFlow` resolves `BetterFeedback.of(context)`, so the host MUST wrap the app root in `feedback`'s `BetterFeedback` widget or it throws. `feedback`'s screenshots require Flutter's CanvasKit renderer on web, and platform views (maps, webviews) render blank in the captured PNG. `AppBoxKitLocalFileSubmissionSink` uses `dart:io`, so on web inject a `AppBoxKitCallbackSubmissionSink` instead; the `AppBoxKitEmailSubmissionSink` and `AppBoxKitGithubIssueSink` are deliberate stubs that throw `UnimplementedError` — wire a real transport before relying on them. Because the `Talker` is injected, passing a fresh/empty instance ships a diagnostics bundle with no history — hand the service the same singleton the app logs to.


### Testing

`import 'package:appbox_kit_support/appbox_kit_testing.dart';` for
`RecordingAppBoxKitSubmissionSink` (records `submissions`, scriptable `result`),
`appBoxKitFakeFeedbackSubmission(...)`, and `appBoxKitCannedDiagnosticsBundle(...)` — assert the
diagnostics/submit path without a widget tree or a real Talker.

### Decisions / ADRs

The package backs onto `feedback` for the screenshot+annotation flow (its overlay and editor are mature and self-contained) and onto `talker_flutter` for diagnostics precisely because appbox_kit apps already register a `Talker` as a lazy singleton — reusing that instance avoids a competing logger and ships the same log history the app has been writing. It is intentionally standalone (no `appbox_kit` core, `stacked`, or `stacked_services` edge) so a host can adopt in-app support without pulling the rest of the kit, and it is not a crash reporter — Crashlytics/Sentry stay a separate concern. The default sink is `AppBoxKitLocalFileSubmissionSink` (app-documents files) because it carries no transport dependency; the email and github-issue sinks ship as stubs so the package never pulls an SMTP/HTTP client until a host explicitly opts in. The `AppBoxKitSubmissionSink` port exists so a host can swap in Supabase, an existing HTTP client, or a web-friendly callback without forking the service.
