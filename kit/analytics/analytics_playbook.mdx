### Usage & wiring

Add the package as a path dependency (`appbox_kit_analytics: { path: ../analytics }`, since it is `publish_to: 'none'`), import the barrel, and construct `KitAnalyticsService` with the backends you want — `DebugConsoleAnalyticsBackend` ships as the working default. The service is intentionally not a Stacked service and has no dependency on `stacked`, `stacked_services`, or `appbox_kit` core, so register the constructed instance on your app's locator however you wire singletons (the kits resolve through the shared `StackedLocator.instance`). Minimal usage:

```dart
import 'package:appbox_kit_analytics/appbox_kit_analytics.dart';

final analytics = KitAnalyticsService(
  backends: [DebugConsoleAnalyticsBackend()],
);

await analytics.logEvent('checkout_completed', params: {'total_cents': 4200});
await analytics.screenView('Cart', screenClass: 'CartView');
await analytics.timing('time_to_interactive', const Duration(milliseconds: 830));
```

### Architecture

`KitAnalyticsService` is the single entry point and depends only on its own value objects — it normalizes each call into a `KitAnalyticsEvent` / `KitScreenView` / `KitUserProperty` / `KitAnalyticsTiming` and fans it out, via `Future.wait`, to every registered `KitAnalyticsBackend` held in an id-keyed map. `KitAnalyticsBackend` is the abstract port each destination implements, so the dependency direction is backends → port, never the service → a vendor SDK. Each backend call is wrapped in a try/catch so one throwing backend is isolated (routed to `onError`, default `debugPrint`) and the remaining backends still receive the call. The package is deliberately not a Stacked service and has no dependency on `appbox_kit` core, `stacked`, or `stacked_services`.


### Gotchas

This package is pure Dart with zero native dependencies, so it requires no permissions, manifest keys, or platform channels — any native setup belongs to the vendor SDK a host opts into, not here. The Firebase / Amplitude / PostHog backends are `UnimplementedError` stubs: registering one before implementing it will throw on every call (caught and reported, but the event is lost), and each stub documents a 2026-verified target version (`firebase_analytics ^12.1.1`, `amplitude_flutter ^4.6.1`, `posthog_flutter ^5.24.2`) that will need re-pinning as those SDKs move. Note also that `registerBackend` replaces any existing backend with the same `id` (last registration wins), `DebugConsoleAnalyticsBackend` is suppressed in release by default (`enableInRelease: false`), and fan-out is awaited as a group so one slow backend stalls the whole call.

### Decisions / ADRs

The kit chose a **native-first / standalone** stance: it depends on neither `appbox_kit` core, `stacked`, nor `stacked_services`, shipping only a pure-Dart port plus the zero-dependency `DebugConsoleAnalyticsBackend`. The vendor backends (Firebase / Amplitude / PostHog) are kept as real-signature file stubs rather than wired dependencies so this package's dependency graph stays minimal and `flutter pub get` resolves without pulling any vendor SDK — a host pays that cost only when it opts in. Consent / opt-out gating, offline queuing, and A/B assignment were explicitly deferred as app- or backend-level concerns.
