### Usage & wiring

```dart
import 'package:appbox_kit_deploy/appbox_kit_deploy.dart';

const runner = AppBoxKitIoProcessRunner();
final service = AppBoxKitDeployService(targets: [
  const AppBoxKitShorebirdTarget(runner, mode: AppBoxKitShorebirdMode.release),
  const AppBoxKitCloudflarePagesTarget(runner),
]);

final config = AppBoxKitDeployConfig(
  projectName: 'showcase',
  flutterVersion: '3.24.0',
  dartDefines: {'ENV': 'prod'},
  environment: {'CLOUDFLARE_API_TOKEN': token},
);

final checks = await service.doctor(config);   // preflight
final result = await service.deployTo('cloudflare-pages', config);
```

CLI: `dart run appbox_kit_deploy doctor` /
`dart run appbox_kit_deploy deploy cloudflare-pages --project-name=showcase`.

### Architecture

`AppBoxKitDeployService` is a facade holding a name-indexed map of `AppBoxKitDeployTarget`s: `doctor(config)` fans out to every registered target, while `deployTo(name, config)` routes to a single target by key (throwing `ArgumentError` for an unknown name). Each target implements the `AppBoxKitDeployTarget` interface and depends only on the `AppBoxKitProcessRunner` port — never on `dart:io` directly — so `AppBoxKitIoProcessRunner` is the production adapter and `ScriptedAppBoxKitProcessRunner` is the test double. Dependency direction is strictly inbound and standalone: `AppBoxKitDeployConfig` flows in, `AppBoxKitDeployResult` / `AppBoxKitDoctorCheck` flow out, and the package pulls in no `flutter`, `stacked`, or `appbox_kit` dependency.


### Gotchas

The external CLIs (`flutter`, `bundle`/`fastlane`, `shorebird`, `wrangler`, `vercel`) must be on `PATH` — `AppBoxKitIoProcessRunner` shells out with `runInShell: true`, and a missing binary surfaces as `exitCode: 127` (caught from `ProcessException`) rather than a thrown Dart error. Secrets and tokens are passed via `AppBoxKitDeployConfig.environment` (e.g. `CLOUDFLARE_API_TOKEN`, `VERCEL_TOKEN`) and forwarded to each subprocess; they are never hard-coded. Two target-specific pitfalls: `AppBoxKitVercelTarget` runs `flutter build web --release` then `vercel deploy build/web --prod --yes` — Vercel CLI v55+ tightened non-interactive project linking, so pin a CLI major version (`doctor` reports `vercel --version`) and set `VERCEL_ORG_ID` / `VERCEL_PROJECT_ID` to link non-interactively — and `AppBoxKitCloudflareWorkersTarget` runs `wrangler deploy` with no flutter build step, reading the Worker's own `wrangler.toml` from `workingDirectory` (failing with `ok: false` when it is null) and needing `CLOUDFLARE_API_TOKEN` + `CLOUDFLARE_ACCOUNT_ID`. Real tool failures do not throw — targets return `AppBoxKitDeployResult(ok: false, failureReason: ...)`. Note: the README lists no native permission or manifest keys, because this package orchestrates CLIs rather than shipping a platform plugin — iOS/Android signing, shorebird app IDs, and lane-specific credentials live in the host app and its fastlane configuration.

### Decisions / ADRs

`kit_matrix.md` sets "standalone by default" as the project-wide rule — new kits depend on neither `appbox_kit`, `stacked`, nor `stacked_services` — and records `appbox_kit_deploy` as `{role: deploy-tooling, deps_kit: [], backing: []}`. Deploy takes that stance furthest: zero kit dependencies and zero backing Dart packages, because it shells out to external CLIs through the `AppBoxKitProcessRunner` port instead of binding their SDKs. That port is the load-bearing decision — it keeps the package pure Dart (runnable as `dart run appbox_kit_deploy`), and lets every command shape be asserted with `ScriptedAppBoxKitProcessRunner` so CI needs no Flutter/fastlane/shorebird toolchain installed.
