### Overview & role

Native-first payments for appbox_kit apps — Apple Pay + Google Pay via Google's first-party pay plugin, behind a pluggable provider port so Stripe/PayPal backends slot in later. Typed AppBoxKitPaymentResult, scriptable fakes.

### Usage & wiring

```dart
import 'package:appbox_kit_payments/appbox_kit_payments.dart';

final payments = DefaultAppBoxKitPaymentsService.native(
  applePay: const AppBoxKitApplePayConfig.fromAsset('assets/apple_pay_config.json'),
  googlePay: const AppBoxKitGooglePayConfig.fromAsset('assets/google_pay_config.json'),
);

if (await payments.canPay(AppBoxKitPaymentMethod.applePay)) {
  final result = await payments.requestPayment(
    config: const AppBoxKitApplePayConfig.fromAsset('assets/apple_pay_config.json'),
    items: const [AppBoxKitPaymentItem(label: 'Total', amount: '99.99')],
  );
  switch (result) {
    case AppBoxKitPaymentSuccess(:final token):   // forward token to your server / PSP
    case AppBoxKitPaymentCancelled():             // user dismissed — do nothing
    case AppBoxKitPaymentDeclined(:final reason): // retry with another method
    case AppBoxKitPaymentError(:final message):   // log; not user-fixable
  }
}
```

Or drop in the button directly:

```dart
AppBoxKitPayButton(
  applePay: const AppBoxKitApplePayConfig.fromAsset('assets/apple_pay_config.json'),
  googlePay: const AppBoxKitGooglePayConfig.fromAsset('assets/google_pay_config.json'),
  items: const [AppBoxKitPaymentItem(label: 'Total', amount: '99.99')],
  onResult: (result) { /* same switch as above */ },
);
```

### Architecture

Hosts depend only on the `AppBoxKitPaymentsService` port (`canPay` + `requestPayment`) and the sealed `AppBoxKitPaymentResult`; `DefaultAppBoxKitPaymentsService` routes each call through a `AppBoxKitPaymentsProviderRegistry` to the first registered `AppBoxKitPaymentsProvider` whose `supportedMethods` contains the requested wallet. `AppBoxKitPayPaymentsProvider` is the sole live adapter, wrapping the `pay` plugin, while `AppBoxKitStripePaymentsProvider` and `AppBoxKitPayPalPaymentsProvider` ship as same-shaped stubs that throw `UnimplementedError` until their phase arrives. Dependency direction is strictly models/service → providers → `pay`: the service and ViewModels carry no provider SDK, so backends can be swapped without touching call sites. The package is also standalone — it declares no dependency on `appbox_kit`, `stacked`, or `stacked_services`.


### Gotchas

Native setup is yours to own: Apple Pay requires the Apple Merchant ID entitlement and a matching `merchantIdentifier` in the profile JSON, and Google Pay requires merchant approval in the Google Pay & Wallet Console plus the gateway wiring in the Android manifest — this package ships the flow, not the merchant onboarding. The sample profiles under `example/` (`apple_pay_config.json`, `google_pay_config.json`) must be copied into the host app's own `assets/` and declared in its pubspec; no payment profile is bundled here. Note that Apple/Google Pay do not distinguish a card decline client-side, so a declined instrument surfaces as `AppBoxKitPaymentError`, not `AppBoxKitPaymentDeclined` — the decline-vs-error split only becomes meaningful once the Stripe/PayPal stubs (currently `UnimplementedError`) are implemented. This package only mints a wallet token; capturing/charging it is your server's job (an explicit non-goal), and it targets Android + iOS only — the `pay` plugin supports no other platform.

### Decisions / ADRs

The package backs itself with Google's first-party `pay` plugin because it wraps PassKit and the Google Pay API directly, driving the wallet the user already trusts without putting a third-party PSP SDK in the hot path. It ships standalone (no dependency on `appbox_kit`, `stacked`, or `stacked_services`) so the payments surface stays usable from non-stacked apps and is not coupled to the framework's release cadence — `pay ^3.3.0` is its only backing dependency. Stripe and PayPal were left as same-shaped stubs behind the `AppBoxKitPaymentsProvider` port rather than baked in, so a real PSP backend can be added later without changing any call site: native-wallet coverage first, PSP capture deferred to the layer that actually owns it (your server).
