### Usage & wiring

This is a standalone Flutter app run with `flutter run` from `showcase_app/`, not a published package. `main()` calls `setupLocator(stackedRouter: kitPlatformRouter)`; the `@StackedApp` annotation in `lib/app/app.dart` drives codegen for the routes and the lazy-singleton dependencies — `KitBottomSheetService` registered `asType: BottomSheetService`, plus `KitThemeService`, `KitErrorService`, `KitHapticService`, `KitNotificationService`, `Talker`, and the app's own `NotesService` / `NotesMediaService`. Boot finishes `KitThemeService.initialize()`, `setupKitSnackbars()`, `setupDialogUi()`, and `setupBottomSheetUi()` before `runApp(const ShowcaseApp())`, whose `MaterialApp.router` wires `kitPlatformRouter` (a `KitPlatformPagesMixin` subclass over the generated `StackedRouterWeb`) for per-platform page types. The data-layer boot (`AppData.initialize()`) runs later inside `ShowcaseStartupViewModel.runStartupLogic()`, which then replaces onto `ShowcaseShellViewRoute()`.

### Architecture

The app is a navigator2 shell-per-tab architecture: `ShowcaseShellView` hosts four nested stacks (Home, Search, Profile, Notes) in a `StackedTabsRouter` — stacked's IndexedStack model, so every tab stays alive across switches and tab taps call `setActiveIndex` rather than pushing. The shell owns only the body outlet and the `KitNativeTabBar`; each tab owns its own chrome (app bar / FAB) so switching reveals an already-mounted `Scaffold` with no teardown or fade. The shell mounts the bar per the tab-shell chrome contract — `Scaffold(extendBody: true, body: KitExtendBodyFabLift(child: <outlet>), bottomNavigationBar: KitNativeTabBar(...))` (or `KitBottomNavScaffold` from `ui_library`, which composes all three): `extendBody` lets content scroll under the translucent glass bar, and `KitExtendBodyFabLift` mirrors the bar height into `MediaQuery.viewPadding` so per-tab FABs float clear of it. Stock `BottomNavigationBar`/`NavigationBar`/`CupertinoTabBar` and extendBody-less kit tab bars are pipeline rejects (`review_checklist.sh` check 1c). Top chrome follows the same kit-first split: EVERY surface mounts `KitNativeAppBar` in `Scaffold.appBar` — one app bar across the app, never stock `AppBar`/`CupertinoNavigationBar`, never any `SliverAppBar` (the kit `KitNativeSliverAppBar` is ui_library inventory, not app chrome); a scrollable leaf keeps the same fixed bar above its `CustomScrollView` body — the Notes folder view is the exemplar; stock bars and sliver bars are pipeline rejects (`review_checklist.sh` checks 1d/1e, presence via 1t). Dependency direction is strictly app → kit: `appbox_kit_*` and `ui_library` resolve via path deps, service registration lives in the app's `@StackedApp` (decoupled from the kits), and `NotesService` / `NotesMediaService` are app-side facades over the `appbox_kit_data` seed backend booted in `AppData.initialize()`. `ScreenTypeLayout.builder` selects mobile / tablet / desktop variants per view, and `KitPlatformRouter` mixes in `KitPlatformPagesMixin` to emit Cupertino pages on iOS and Material pages on Android.


All behavior discriminators are typed, and every `enum` / sealed discriminator type lives under `lib/enums/` — per-shell folders with shell barrels (`showcase_application_enums`, `showcase_notes_enums`, `showcase_profile_enums`, `showcase_startup_enums`) re-exported by a root `enums.dart` that exports nothing else. Route-param actions, tab identity, rail/segment selections, dialog results, and motion presets are enums (enhanced where they carry label/route/preset fields); abxAction op names are per-owner op-verb enums (`ShowcaseNotesFacadeOp`, `ShowcaseNotesMediaOp`) whose `.name` is the camelCase hub/mutate wire key, with facade op enums carrying their mutate copy (`error`, nullable `success`) as fields; mixed domains of sentinels plus an open id set (folder scope `'all' | 'trash' | <uuid>`) are sealed types with a route-boundary `parse` and exhaustive switches. Views, widgets, viewmodels, and services all import the enums barrels (pure types — the view↔viewmodel purity rule is unaffected), and arch_guard's G12 flags any enum/sealed declaration outside `lib/enums/**`.


### Gotchas

Notes media requires native permission strings: iOS `Info.plist` carries `NSMicrophoneUsageDescription`, `NSCameraUsageDescription`, and `NSPhotoLibraryUsageDescription`, and the Android `AndroidManifest.xml` declares `RECORD_AUDIO` (camera capture goes through `image_picker`'s intent and needs no Android permission). The `dependency_overrides` block is load-bearing — overrides do not propagate to a standalone package, so without the vendored `fab_m3e` / `split_button_m3e` / `toolbar_m3e` / `navigation_rail_m3e` forks and the `win32` ^6 / `device_info_plus` ^13 / `package_info_plus` ^10 pins, the m3e forks silently revert to their pub.dev releases and the win32-family version conflict fails resolution outright. `uses-material-design: true` is required (the app bundles the `MaterialIcons` font) or Material icons render as tofu across appbox_kit and the M3E packages. Web / desktop / tablet variants are intentional responsive stubs kept unimplemented as a form-factor showcase, not bugs. In-shell back navigation must be `context.popRoute()` — it delegates to `topMostRouter.pop()`, popping the shell's nested stack (editor → folder, tab bar stays put); `context.router.navigateBack()` replays the root `navigationHistory` and lands on shell-level entries, escaping the tab shell (the note-editor and notes-folder mobile leaves are the exemplars; `review_checklist.sh` check 1h enforces this).

### Decisions / ADRs

The showcase is `publish_to: 'none'` and stands alone so it can exercise the full kit graph as one consumer — every `appbox_kit_*` package resolves via path deps (Task #7 reconciliation: mirroring the upstream app root so conflicts surface at `pub get` time, not at publish). The default `AppData` config boots the seed backend with snapshot persistence and fake auth precisely so a supabase / appwrite config can be dropped in to smoke-test a real backend with zero other code changes. Per-platform native chrome is delivered by `KitPlatformRouter` mixing in `KitPlatformPagesMixin` (Cupertino pages on iOS, Material on Android, no-animation on web), and the vendored m3e forks fold their upstream patches into this universe. Web / desktop / tablet shells are deliberately left as stubs to document the form-factor boundary rather than as debt.
