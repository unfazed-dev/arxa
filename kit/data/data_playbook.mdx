### Usage & wiring

Add `arxa_kit_data` as a path dependency (`path: ../data` from a sibling host), then call `ArxaKitData.initialize` once in `main()` after `setupLocator()` — the kit never self-registers, so the host owns the call. Pass one `ArxaKitEntityRegistration<T>` per model (a plain model plus `fromJson`/`toJson`; the storage mapping lives on the `ArxaKitTableSchema`, never the model) and the fixture asset paths; `initialize` switches on `ArxaKitDataConfig.backend` and registers one `ArxaKitRepository<T>` per entity into the shared `StackedLocator.instance` (plus `ArxaKitAuthService` when `auth:` is set). ViewModels then resolve them directly, e.g. `arxaKitLocator<ArxaKitRepository<Product>>()`, or through a `ArxaKitDataFacade` subclass for derived streams and `mutate(...)`-driven writes.

```dart
await ArxaKitData.initialize(
  config: const ArxaKitDataConfig(backend: ArxaKitDataBackend.seed),
  entities: [productRegistration],
  fixtureAssets: ['assets/seed/products.json'],
);
final products = arxaKitLocator<ArxaKitRepository<Product>>();
```

### Architecture

```
View → ViewModel → Facade Service → Repository → Backend
```

- **Repository** (`ArxaKitRepository<T>`) is the swap seam: one interface,
  three backend implementations (`ArxaKitSeedRepository`, `ArxaKitSupabaseRepository`,
  `ArxaKitAppwriteRepository`). No codegen.
- **Facade Service** (`ArxaKitDataFacade` subclass) is the only layer ViewModels
  talk to. It composes repositories into derived streams and routes
  mutations through `ArxaKitAction` via `mutate(...)`.
- Only one Backend is active per app run, chosen by `ArxaKitDataConfig.backend`
  (default `ArxaKitDataBackend.supabase`).


### Gotchas

The host must mirror three `dependency_overrides` into its own `pubspec.yaml` (`win32: ^6.0.1`, `device_info_plus: ^13.0.0`, `package_info_plus: ^10.0.0`) — pub overrides don't propagate, and missing them breaks desktop `flutter test` (`win32_registry 2.x` won't compile against `win32 6.x`); the Windows FFI involved never runs on iOS/Android/web/macOS. Any file defining a `ArxaKitTableSchema` or `ArxaKitEntityRegistration` must use targeted imports, never the `arxa_kit_data` barrel — the barrel re-exports the Supabase/Appwrite adapters, whose FFI/native-asset deps crash the pure-Dart kernel compile inside `dart run` generators. The ADR-0001 namespace is load-bearing: changing it on a host that already stores rows orphans every primary key, every foreign-key reference, and breaks idempotent re-seeding. On the auth side, Fake Auth is seed-only (Supabase RLS and Appwrite default-deny reject it); Supabase Google needs `googleServerClientId` plus Android SHA fingerprints and the iOS URL scheme, while Appwrite OAuth runs as a browser flow behind the `appwrite-callback-<PROJECT_ID>` URL scheme.


### Testing

The test seam is the AssetBundle inversion: `ArxaKitAssetReader` is a pure-Dart port, so tests inject a `ArxaKitMemoryAssetReader({...})` of fixture JSON (and `ArxaKitData.initialize(assetReader: ...)` accepts it) and exercise the entire seed path under `flutter test` or `dart run` with no Flutter binding. The suite favors real components over scripted mocks — a real `ArxaKitSeedStore` backed by `ArxaKitNoPersistence` is the usual substrate — so assertions are on stream emissions (`emitsInOrder`) and on `tableSnapshot` row contents, not on mock call-counts. `ArxaKitData.resetForTesting()` clears the composition root between cases.

### Decisions / ADRs

**ADR-0001 — Deterministic UUID v5 canonical IDs** (accepted, hard-to-reverse): every Seed Key becomes `uuid.v5(namespace, '<table>:<key>')`, so one fixture yields byte-identical primary keys on Seed, Supabase, and Appwrite and re-seeding is idempotent everywhere; the namespace is persisted as Postgres PKs / Appwrite row IDs, so changing it breaks every stored row. Rejected alternatives were random v4 plus a key→uuid mapping artifact (adds a sync problem), raw semantic keys as PKs (invalid for Postgres `uuid`, leaks authoring into storage), and per-backend native ID generation (the same row gets different IDs per backend). The package ships as `publish_to: 'none'` on a path dep, pairing `supabase_flutter` and `appwrite` behind one `ArxaKitRepository<T>` port with no codegen, so the active backend is a runtime swap rather than a fork — see `kit_matrix.md` for the full decisions log.
