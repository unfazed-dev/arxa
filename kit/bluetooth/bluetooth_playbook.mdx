### Usage & wiring

Add `arxa_kit_bluetooth` to your `pubspec.yaml` and run `flutter pub get`. The package is **standalone** — no path dependency on any kit, no `setupLocator`, no codegen — so you construct the production binding directly and register it into your host app's locator (`StackedLocator.instance`, the same singleton the generated `locator` uses):

```dart
import 'package:arxa_kit_bluetooth/arxa_kit_bluetooth.dart';

final ArxaKitBluetoothService bluetooth = ArxaKitFlutterBluePlusBluetoothService();
// register once during app bootstrap:
locator.registerSingleton<ArxaKitBluetoothService>(ArxaKitFlutterBluePlusBluetoothService());
```

Consume the live adapter stream and branch the enable path off the capability gate (`canControlAdapter` is `true` on Android, `false` on iOS):

```dart
bluetooth.adapterState.listen((s) { /* rebuild on poweredOff / poweredOn / … */ });
if (bluetooth.capabilities.canControlAdapter) {
  await bluetooth.requestEnable();   // Android: system enable dialog
} else {
  await bluetooth.openSettings();    // iOS: escort to Bluetooth settings
}
```

### Architecture

`arxa_kit_bluetooth` is a hexagonal port-and-adapter package. `ArxaKitBluetoothService` is the implemented port (with `ArxaKitBluetoothScanner` and `ArxaKitBluetoothGattClient` as phase-2 ports whose `Unimplemented*` stubs throw on every call); `ArxaKitFlutterBluePlusBluetoothService` is the sole production adapter, wrapping `flutter_blue_plus` for adapter-state observation and `app_settings` for the iOS settings escort. Dependency direction points one way only — consumers depend on the ports and the Kit-prefixed value types (`ArxaKitBluetoothAdapterState`, `ArxaKitBluetoothDevice`, …), while the adapter alone imports `flutter_blue_plus`, so no plugin types leak across the seam. The package is standalone by design: it depends on no other kit and not on `stacked`/`stacked_services`, keeping it a pure port over a native plugin.


### Gotchas

`flutter_blue_plus` is a direct wrapper over the OS Bluetooth stacks; this
package ships no custom native code. The escort contract holds: adapter state
always comes from the live OS stream, never cached UI state.


### Testing

`package:arxa_kit_bluetooth/arxa_kit_testing.dart` exports `FakeArxaKitBluetoothService`:
drive the adapter stream with `emit`, choose the capability set, and assert the
escort via `openSettingsCallCount` / `requestEnableCallCount`. On the
`escortOnly` capability set `requestEnable` throws so the escort branch is
exercisable.

### Decisions / ADRs

`flutter_blue_plus` was chosen because it is native-first — a direct wrapper over CoreBluetooth (iOS) and `android.bluetooth` (Android) — so this package ships no custom native code of its own; it is pinned at `^2.3.10` (verified on pub.dev 2026-07-14). `app_settings` (`^7.0.0`) backs only the Bluetooth settings deep-link used by the iOS escort flow. The standalone stance (no path dependency on `arxa_kit_permissions` or any other kit, and no `stacked`/`stacked_services` dep) keeps this a pure plugin-neutral port: swapping the backing plugin later touches only `ArxaKitFlutterBluePlusBluetoothService`, never its consumers. The Android 12+ `BLUETOOTH_CONNECT`/`BLUETOOTH_SCAN` runtime-permission wiring is deliberately deferred to the downstream reconciliation pass rather than pulled in here.
