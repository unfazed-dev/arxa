### Overview & role

API-first auth seam for appbox_kit apps — a KitAuthService port (email/password + OAuth), typed AuthResult with failure reasons, an in-memory default backend, and scriptable fakes. Seed-backend and native OAuth wiring are later phases.

### Usage & wiring

```dart
import 'package:appbox_kit_auth/appbox_kit_auth.dart';

final auth = InMemoryKitAuthService();

auth.authStateChanges.listen((user) {
  // null = signed out (also how token-expiry surfaces).
});

final result = await auth.signIn(
  const EmailPasswordCredentials(email: 'a@b.com', password: 'hunter2'),
);
switch (result) {
  case AuthSuccess(:final user):    // signed in
  case AuthFailure(:final reason):  // branch on reason (userNotFound, …)
}
```

### Architecture

`KitAuthService` is the single port — an `abstract interface class` exposing `authStateChanges`, `currentUser`, `signUp`, `signIn`, `signInWithApple`, `signInWithGoogle`, `signOut`, and `dispose`; failures come back as typed `AuthResult` rather than thrown exceptions (only programming errors like using a disposed service throw). `InMemoryKitAuthService` is the sole concrete adapter today — a process-lifetime identity store with no persistence and no network — while `SeedAuthBackend` and the `KitOAuthProvider` stubs are ports that future backends compose behind the same service. Dependency direction is strictly inbound: the models (`AuthUser`, `AuthSession`, `AuthResult`) and the port sit at the centre, the adapter depends on the port, and call sites (ViewModels) depend only on the port and never on a backend SDK.


### Gotchas

No native platform setup is required today: the `AppleSignInProvider` / `GoogleSignInProvider` stubs throw `UnimplementedError`, so there are no iOS entitlements, `GoogleService-Info.plist`, or Android manifest keys to configure until the phase-later OAuth wiring lands. The main pitfall is treating `InMemoryKitAuthService` as production-grade — passwords live in plaintext in memory and are lost on restart, and the README explicitly marks it a build-time convenience, not a security boundary (no real hashing, session persistence, RBAC, or account recovery). Watch the naming collision: `appbox_kit_data` also ships a `KitAuthService` (a different, backend-coupled variant with `session$`/`currentSession`); the repo has zero co-imports today, but if a workspace ever imports both it must prefix-import (`as`) one of them — full reconciliation is a Phase-4 fold, not this package's job.


### Testing

```dart
import 'package:appbox_kit_auth/testing.dart';

final auth = FakeKitAuthService(
  scriptedResults: [
    AuthSuccess(AuthSession(user: AuthUser(id: 'u1', email: 'a@b.com'))),
    const AuthFailure(AuthFailureReason.tokenExpired),
  ],
);

// Drive token-expiry directly:
auth.expireSession();               // emits signed-out on authStateChanges
```

Factories: `FakeKitAuthService.signedIn(user)`, `.signedOut()`,
`.alwaysFails(reason)`. `FakeKitAuthService.expiredSession(user)` builds an
already-expired `AuthSession` for `AuthSession.isExpiredAt` assertions.

### Decisions / ADRs

The package is deliberately standalone: it depends on the Flutter SDK only, with no dependency on `stacked`, `stacked_services`, `appbox_kit`, or any app code, so the auth seam can be adopted (or swapped out) without pulling in the rest of the kit graph. OAuth backing SDKs are chosen but deferred — `sign_in_with_apple ^8.1.0` and `google_sign_in ^7.2.0` are the picked providers, kept as a non-breaking later add behind the `KitOAuthProvider` port rather than a hard dependency today. The `SeedAuthBackend` seam is held interface-clean on purpose: it will never import app code, and the host injects the operations it needs, so a real backend can land in Phase 4 without coupling this package to the host's identity layer.
