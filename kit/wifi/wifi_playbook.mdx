### Usage & wiring

This package is a **standalone port** — it depends on no other kit (not `appbox_kit`, `stacked`, or `stacked_services`), so there is no locator or `@StackedApp` registration step. Add the dependency, then construct `ConnectivityAppBoxKitWifiService` directly (optionally injecting `Connectivity` / `NetworkInfo` for tests) and hold it in whatever ViewModel or service needs it. Minimal usage: listen to `stateChanges` for the live OS connectivity stream, call `currentNetwork()` for a best-effort SSID/IP read, and reach the escort via `openSettings()` — or catch `AppBoxKitWifiUnsupportedError` from `requestEnable()` and fall back to `openSettings()`. No in-package permission wiring ships here; the SSID-read location-permission dependency is deferred to a downstream reconciliation pass.

### Architecture

`AppBoxKitWifiService` is the abstract interface **port** (`stateChanges`, `currentState`, `currentNetwork`, `capabilities`, `requestEnable`, `openSettings`); `ConnectivityAppBoxKitWifiService` is the sole production **adapter**, binding the port to `connectivity_plus` (the live stream), `network_info_plus` (on-demand SSID/BSSID/IP), and `app_settings` (the Wi-Fi settings deep-link). Value types model the observable surface — `AppBoxKitWifiState` (connected/disconnected/unknown), `AppBoxKitWifiNetwork` (nullable SSID/BSSID/IP), `AppBoxKitWifiCapabilities` (the direct-vs-escorted gate) — and `AppBoxKitWifiUnsupportedError` signals unsupported adapter control. Dependency direction is one-way inward: the adapter depends on the port plus the three backing plugins, the port depends on nothing, and the whole package depends on no other kit — so callers can swap `ConnectivityAppBoxKitWifiService` for `FakeAppBoxKitWifiService` without touching any Stacked wiring.


### Gotchas

`AppBoxKitWifiState` reflects **reachability, not radio power**: `disconnected` does not prove the adapter is off — on-but-idle is indistinguishable from off from inside the app, and `connected` only implies the adapter is on. SSID/BSSID reads are location-permission gated on modern iOS and Android (plus iOS entitlements), so a `null` SSID on a `connected` device usually means permission denied rather than "no network"; treat `AppBoxKitWifiNetwork` as a hint, never authoritative. `requestEnable()` throws `AppBoxKitWifiUnsupportedError` on iOS and Android 10+ (no cross-platform OS API enables the radio) — the UI must catch it and call `openSettings()` instead. No native manifest keys are documented in this package and the location-permission wiring is not included; both are deferred to the downstream reconciliation pass.


### Testing

`package:appbox_kit_wifi/appbox_kit_testing.dart` exports `FakeAppBoxKitWifiService`: drive the
stream with `emit`, set `currentNetwork` with `setNetwork`, and assert the
escort via `openSettingsCallCount` / `requestEnableCallCount`. `requestEnable`
throws by default (adapter uncontrollable) so the escort branch is exercisable.

### Decisions / ADRs

**Why `connectivity_plus` for the stream:** `network_info_plus` is request/response only — it has no stream, and polling `getWifiName()` would both violate the "real OS stream, never cached" contract and misreport "off" whenever location permission is denied (SSID reads return `null`). The live `Stream<AppBoxKitWifiState>` therefore comes from `connectivity_plus` (Android `ConnectivityManager` / iOS `NWPathMonitor`); `network_info_plus` is used only for the on-demand SSID/IP read, and `app_settings` only for the escort deep-link. **Why standalone:** the package is a pure port over native plugins, so it deliberately takes no path dependency on `appbox_kit_permissions` (or any kit), letting app code adopt or test it without pulling `stacked`, `stacked_services`, or the wider kit matrix. **Stubbed by design:** direct adapter control (`requestEnable`) and programmatic network-join are non-goals — no mobile OS exposes a cross-platform API for either.
